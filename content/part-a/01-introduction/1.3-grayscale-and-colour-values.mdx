## 2. What is grayscale?

**Grayscale** means an image containing different levels of brightness from black to white, without colour information.

## 7. RGB values

Each colour channel can usually have a value from **0 → 255**. So a colour pixel contains **[R, G, B]**. For example, `[255, 0, 0]` means R = 255, G = 0, B = 0. Therefore: **red**.

<ChannelOrder order="RGB" values={[255, 0, 0]} />

## 8. Pure green

Consider `[0, 255, 0]`: R = 0, G = 255, B = 0. So: **green**.

<ChannelOrder order="RGB" values={[0, 255, 0]} />

## 9. Pure blue

`[0, 0, 255]` means R = 0, G = 0, B = 255. Therefore: **blue**.

<ChannelOrder order="RGB" values={[0, 0, 255]} />

## 10. Black in RGB

What if all three channels are zero? `[0, 0, 0]`: there is no red light, no green light and no blue light. Therefore: **black**.

<ChannelOrder order="RGB" values={[0, 0, 0]} />

## 11. White in RGB

Now `[255, 255, 255]`: R = 255, G = 255, B = 255. All three are at maximum intensity. Therefore: **white**.

<ChannelOrder order="RGB" values={[255, 255, 255]} />

## 12. Gray in RGB

Here's something interesting. Consider `[128, 128, 128]`: all three channels have the same value. The result is **gray**.

This is mostly a historical / software convention rather than something fundamental about how colours work. You do not need to think *"BGR is a better colour model than RGB."* It isn't. They're simply different channel orderings.

OpenCV provides:

## 25. Grayscale conversion

Now suppose we have a colour image (R, G, B) and we want grayscale (one brightness value). We cannot simply say `gray = R + G + B`, because that could exceed 255.

And more importantly, humans don't perceive all colours as equally bright. For example, **pure green** appears brighter to our eyes than **pure blue**.

<SwatchRow items={[{ value: [0, 255, 0], label: "pure green", sub: "looks brighter" }, { value: [0, 0, 255], label: "pure blue", sub: "looks darker" }]} />

So grayscale conversion uses a **weighted** combination of the colour channels. A common luminance approximation is:

```text
Y ≈ 0.299 R + 0.587 G + 0.114 B
```

Don't worry about memorizing the formula yet. The important idea is:

/>

Because our visual system is more sensitive to some wavelengths than others. Very roughly:

## 28. Why convert colour images to grayscale?

Many computer vision algorithms don't need colour. For example:

<Chips items={["Edge detection", "Thresholding", "Contours", "Morphology", "Shape detection"]} />

often primarily care about **brightness differences** rather than colour information. So we can simplify:

This can reduce the amount of data we process.

## 29. But don't convert everything to grayscale

This is also important. Suppose you're detecting a **red object** against a **green background**. Colour information may be extremely useful. If you throw away colour, you may lose an important distinction.

## Code

We now build colour pixels ourselves, then let OpenCV do the same work.

### 1. A colour image from scratch, in OpenCV's order

```python
import numpy as np

# A 2 × 2 colour image in OpenCV order: [B, G, R] per pixel
image = np.zeros((2, 2, 3), dtype=np.uint8)
image[0, 0] = [0, 0, 255]       # red
image[0, 1] = [0, 255, 0]       # green
image[1, 0] = [255, 0, 0]       # blue
image[1, 1] = [255, 255, 255]   # white

print(image.shape)
print(image[0, 0])
print(image[0, 0, 2], "is the red value of pixel (0, 0)")
```

Output:

```text
(2, 2, 3)
[  0   0 255]
255 is the red value of pixel (0, 0)
```

- `np.zeros((2, 2, 3), dtype=np.uint8)` makes 2 rows × 2 columns × 3 channels, all black.
- `image[0, 0] = [0, 0, 255]` writes all three channels of one pixel. In BGR, `[0, 0, 255]` is red.
- `image[0, 0, 2]` reads one channel of one pixel: channel 2 is red.

### 2. From scratch: BGR to RGB

```python
rgb = np.zeros_like(image)
rows, cols, _ = image.shape
for r in range(rows):
    for c in range(cols):
        b, g, red = image[r, c]          # unpack the three channels
        rgb[r, c] = [red, g, b]          # write them back in reverse order

print(rgb[0, 0])
print(np.array_equal(rgb, image[:, :, ::-1]))
```

Output:

```text
[255   0   0]
True
```

`image[:, :, ::-1]` does the same swap without a loop: it reads the channel axis backwards.

### 3. From scratch: the grayscale formula

```python
b = image[:, :, 0].astype(np.float64)
g = image[:, :, 1].astype(np.float64)
r = image[:, :, 2].astype(np.float64)
gray = np.rint(0.299 * r + 0.587 * g + 0.114 * b).astype(np.uint8)
print(gray)
```

Output:

```text
[[ 76 150]
 [ 29 255]]
```

Pure red becomes 76, pure green 150, pure blue only 29: the weights at work. The channels are converted to `float64` first so the sum cannot overflow.

### 4. The OpenCV way

```python
import cv2

rgb_cv = cv2.cvtColor(image, cv2.COLOR_BGR2RGB)
gray_cv = cv2.cvtColor(image, cv2.COLOR_BGR2GRAY)
print(np.array_equal(rgb_cv, rgb))
print(gray_cv)

b, g, r = cv2.split(image)
print(r)
```

Output:

```text
True
[[ 76 150]
 [ 29 255]]
[[255   0]
 [  0 255]]
```

- `cv2.cvtColor(src, code)` converts between colour representations. `cv2.COLOR_BGR2RGB` swaps the order; `cv2.COLOR_BGR2GRAY` applies the weighted formula and returns one channel.
- The code names the input order: use `BGR2...` for images from `cv2.imread`.
- `cv2.split(image)` returns the three channels as three separate grayscale images, in B, G, R order.

## OpenCV API notes

Versions: OpenCV 4.13.0 (`opencv-python==4.13.0.92`), NumPy 2.5.3. Signatures are copied from the installed library's help text.

| Function | Python signature | Notes |
|---|---|---|
| `cv2.imread` | `imread(filename[, flags]) -> retval` | default `IMREAD_COLOR`: 3 channels, **B, G, R** |
| `cv2.cvtColor` | `cvtColor(src, code[, dst[, dstCn[, hint]]]) -> dst` | `COLOR_BGR2RGB`, `COLOR_BGR2GRAY`, `COLOR_GRAY2BGR`, … |
| `cv2.split` | `split(m[, mv]) -> mv` | one single-channel image per channel |
| `cv2.merge` | `merge(mv[, dst]) -> dst` | the reverse of `split` |

**Facts from the documentation.**

- OpenCV's default colour format "is often referred to as RGB but it is actually BGR": in a standard 24-bit colour image the first byte is blue, then green, then red [4].
- RGB to gray: Y ← 0.299·R + 0.587·G + 0.114·B [3].
- Conventional channel ranges: 0 to 255 for 8-bit (`CV_8U`), 0 to 65535 for 16-bit (`CV_16U`), 0 to 1 for 32-bit float (`CV_32F`) [4].

**Inputs and types.**

- `cv2.imread` without a flag returns 3 channels even for a grayscale file (the gray value is copied into B, G and R). Use `cv2.IMREAD_GRAYSCALE` to get one channel, and `cv2.IMREAD_UNCHANGED` to keep an alpha channel.
- `COLOR_BGR2GRAY` needs a 3- or 4-channel input. A 1-channel input raises an error.
- Grayscale result: 2-D array `(height, width)`. Colour: 3-D `(height, width, 3)`.

**Speed.**

- `image[:, :, ::-1]` is a view (no copy) but not contiguous in memory. Some OpenCV functions need a contiguous array; `cv2.cvtColor(..., COLOR_BGR2RGB)` or `np.ascontiguousarray` gives one.
- A grayscale image is a third of the data of a colour image: three times fewer values to process.

## Where it fails

- **Colour values depend on light and camera, not just the object.** The same orange billet gives different RGB values under different lamps, exposure and white balance. *Instead:* control lighting (59.3), fix camera settings, and correct white balance (10.6).
- **RGB mixes colour with brightness.** In shadow, "red" pixels get lower R, G and B together, so a fixed RGB rule for "red" breaks. *Instead:* colour spaces that separate them, such as HSV and LAB (10.2, 10.3).
- **Saturated pixels lose their colour.** A very bright glowing surface can reach 255 in all channels and become plain white. *Instead:* reduce exposure (2.6), or measure temperature with a thermal camera (Module 46).
- **A colour camera's three values are partly guessed.** Most colour sensors measure one colour per pixel through a Bayer filter, and the other two are interpolated (2.7). Fine colour detail at edges is unreliable. *Instead:* a monochrome camera when colour is not needed (59.1).
- **Gray values are a perception convention, not a light meter.** The weights describe how bright colours *look*, on gamma-encoded values. *Instead:* for physical measurement use linear or radiometric data (see Go deeper; 46.3).

## ⚠️ Common mistakes

**1. Showing a BGR image with Matplotlib.** `plt.imshow(cv2.imread(...))` swaps red and blue. Convert first with `cv2.cvtColor(img, cv2.COLOR_BGR2RGB)`.

**2. Using the wrong conversion code.** `COLOR_RGB2GRAY` on a BGR image applies the red weight to blue and the blue weight to red. For the pixel R = 200, G = 100, B = 50 it gives **96** instead of **124**. Images from `cv2.imread` need `COLOR_BGR2GRAY`.

**3. Converting an image that is already gray.** `cv2.cvtColor(gray, cv2.COLOR_BGR2GRAY)` fails with:

```text
Invalid number of channels in input image:
    'VScn::contains(scn)'
where
    'scn' is 1
```

Check `img.ndim` (2 = gray, 3 = colour) before converting.

**4. Showing a grayscale image with Matplotlib's defaults.** `plt.imshow(gray)` maps single values through a colour map (and stretches them between the image's own min and max), so the picture appears in false colours. Use `plt.imshow(gray, cmap="gray", vmin=0, vmax=255)`.

**5. Adding channels in uint8.** `img[:, :, 0] + img[:, :, 1] + img[:, :, 2]` wraps around: three channels of 200 give **88**, not 600. Convert to a larger type first, or use `cv2.cvtColor`.

**6. Indexing a channel that is not there.** On a grayscale image, `img[0, 0, 0]` raises `IndexError: too many indices for array: array is 2-dimensional, but 3 were indexed`.

**7. Reading a colour pixel as RGB.** `[20, 100, 240]` from `cv2.imread` is orange (R = 240), not blue. Say "B, G, R" out loud when you read OpenCV pixels.

## 🔍 Go deeper

<GoDeeper>

### Why three numbers are enough

The human retina has three types of cone cells, most sensitive to long, medium and short wavelengths. Because colour vision is built on three responses, three well-chosen primaries mixed in different amounts can match a large range of the colours people see. This is the basis of the RGB model used by cameras and displays [1, Ch. 6], [2, Sec. 2.3.2].

### Additive and subtractive colour

Light adds: red + green + blue light gives white (screens, projectors). Inks and paints subtract: they absorb parts of white light, so printers use cyan, magenta and yellow (plus black), and mixing all inks gives dark [1, Ch. 6].

### Where the gray weights come from

The weights 0.299, 0.587, 0.114 come from the television standard ITU-R BT.601 [7]. OpenCV uses them for `COLOR_BGR2GRAY` and `COLOR_RGB2GRAY` [3]. The HD standard ITU-R BT.709 uses different weights: 0.2126, 0.7152, 0.0722 [8]. Both give green the largest share.

These weights are applied to **gamma-encoded** values, so the result is called *luma* (written Y′). It is a good match to perceived brightness, but it is not proportional to the physical amount of light (*luminance*). Chapter 11.3 explains gamma.

### How exactly does OpenCV round?

OpenCV computes 8-bit conversions with integer arithmetic. We checked every one of the 16,777,216 possible 8-bit colours on OpenCV 4.13.0: rounding 0.299 R + 0.587 G + 0.114 B to the nearest integer matched `cv2.cvtColor(..., COLOR_BGR2GRAY)` for all but 22,906 colours, and those differed by exactly 1. For teaching and most applications, the formula is the conversion.

### How the bytes sit in memory

An OpenCV colour image is stored *interleaved*: pixel by pixel, B G R B G R … [4]. For a `uint8` image of width W, channel k of pixel (r, c) is at byte

```text
(r × W + c) × 3 + k
```

so `image.strides` is `(3W, 3, 1)`.

### More bits per channel

16 bits per channel gives 65,536 levels per channel and 48 bits per pixel. OpenCV handles `uint16` images; its conventional range for them is 0 to 65535 [4]. Many industrial and thermal cameras deliver 10, 12 or 16 bits per pixel (see 3.2 and Module 46).

</GoDeeper>
