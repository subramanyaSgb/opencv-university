## 5. Application 2: measurement

Instead of simply asking *"Is it defective?"* we can ask: *"How big is it?"*

<DimSketch name="BILLET" length="1200 mm" width="150 mm" />

A camera system can determine **length = 1200 mm** and **width = 150 mm**. But there's an important point:

<Callout kind="key">

A camera does not automatically know millimetres. **The image gives us pixels.**

</Callout>

We need **calibration or geometry** to convert pixels → physical units. If one pixel covers 1 mm, then:

<Equation terms={[{ value: "1200", label: "pixels" }, { op: "×", value: "1 mm", label: "per pixel" }, { op: "=", value: "1200 mm", result: true }]} />

But if the camera is closer, so that **10 pixels = 1 mm**, the same 1200 pixels mean something else:

<Equation terms={[{ value: "1200", label: "pixels" }, { op: "÷", value: "10", label: "pixels per mm" }, { op: "=", value: "120 mm", result: true }]} />

The pixel count alone says nothing about size until we know the scale.

### 1. From scratch: pixels to millimetres, then a decision

```python
import numpy as np

fov_mm, image_px = 1920.0, 1920          # the camera sees 1920 mm across 1920 pixels
mm_per_px = fov_mm / image_px
edges_px = np.array([212, 1411])          # left and right billet edges found in the image (columns)
length_mm = (edges_px[1] - edges_px[0]) * mm_per_px

nominal, tolerance = 1200.0, 5.0          # order length and allowed error, in mm
status = "PASS" if abs(length_mm - nominal) <= tolerance else "FAIL"
print("mm per pixel:", mm_per_px)
print("length:", length_mm, "mm ->", status)
```

Output:

```text
mm per pixel: 1.0
length: 1199.0 mm -> PASS
```

- `mm_per_px` is the scale from section 5. In a real system it comes from calibration, not from a guess.
- The decision needs a **tolerance**: real measurements are never exactly the nominal value.

### 2. From scratch: a count checked against PLC data

```python
weight_per_m = 2.0       # kg per metre   (from the PLC; example numbers)
rod_length_m = 12.0      # metres
bundle_kg = 576.0        # bundle scale reading

expected = round(bundle_kg / (weight_per_m * rod_length_m))
detected = 24            # from the vision system

print("expected:", expected, "detected:", detected)
print("PASS" if detected == expected else "FAIL")
```

Output:

```text

PASS
```

The vision part produces one number; the decision needs data from the rest of the plant.

### 3. The OpenCV way: same algorithm, two lighting conditions

Download [sample-plate-poor.png](/images/sample-plate-poor.png), [sample-plate-good.png](/images/sample-plate-good.png) and [sample-plate-crack-mask.png](/images/sample-plate-crack-mask.png) (the true crack position) into the folder you run Python from.

```python
import cv2
import numpy as np

truth = cv2.imread("sample-plate-crack-mask.png", cv2.IMREAD_GRAYSCALE)
if truth is None:
    raise FileNotFoundError("Could not read sample-plate-crack-mask.png. Check the path.")
truth = truth > 0

for name in ("sample-plate-poor.png", "sample-plate-good.png"):
    img = cv2.imread(name, cv2.IMREAD_GRAYSCALE)
    if img is None:
        raise FileNotFoundError(f"Could not read {name}. Check the path.")
    t, seg = cv2.threshold(img, 0, 255, cv2.THRESH_BINARY_INV + cv2.THRESH_OTSU)
    found = seg > 0
    hit = np.count_nonzero(found & truth) / np.count_nonzero(truth)
    wrong = np.count_nonzero(found & ~truth)
    print(f"{name}: threshold {t:.0f}, crack found {100 * hit:.0f}%, wrong pixels {wrong}")
```

Output:

```text
sample-plate-poor.png: threshold 129, crack found 84%, wrong pixels 31401
sample-plate-good.png: threshold 64, crack found 100%, wrong pixels 0
```

- `cv2.threshold(img, 0, 255, cv2.THRESH_BINARY_INV + cv2.THRESH_OTSU)` chooses the threshold automatically (Otsu's method, Chapter 13.3) and makes dark pixels white. The `0` is ignored when Otsu is used; the chosen value comes back as `t`.
- Under poor lighting it finds most of the crack but also marks about 31,000 background pixels: unusable. Under controlled lighting it finds the whole crack and nothing else.
- Nothing about the algorithm changed. Only the image did.

### 4. A thermal alarm (simulated data)

```python
import cv2
import numpy as np

H, W = 200, 320
yy, xx = np.mgrid[0:H, 0:W]
temp = 30 + 920 * np.exp(-(((xx - 200) / 45.0) ** 2 + ((yy - 90) / 30.0) ** 2))   # simulated °C

min_t, max_t, _, (x, y) = cv2.minMaxLoc(temp)
print(f"max {max_t:.0f} °C at x={x}, y={y}")
print("pixels above 800 °C:", np.count_nonzero(temp > 800))
print("ALARM" if max_t > 900 else "normal")
```

Output:

```text
max 950 °C at x=200, y=90
pixels above 800 °C: 753
ALARM
```

- The array holds temperatures, not 0–255 brightness values, so it is `float64`. `cv2.minMaxLoc` works on it directly.
- The location comes back as (x, y), as in Chapter 1.2.
- A real system reads these values from a radiometric thermal camera, with emissivity set for the material (Module 46).

## OpenCV API notes

Versions: OpenCV 4.13.0 (`opencv-python==4.13.0.92`), NumPy 2.5.3. Signatures are copied from the installed library's help text.

| Function | Python signature | Used here for |
|---|---|---|
| `cv2.threshold` with `THRESH_OTSU` | `threshold(src, thresh, maxval, type[, dst]) -> retval, dst` | automatic threshold; returns the value it chose |
| `cv2.minMaxLoc` | `minMaxLoc(src[, mask]) -> minVal, maxVal, minLoc, maxLoc` | hottest pixel and its (x, y) |
| `cv2.applyColorMap` | `applyColorMap(src, colormap[, dst]) -> dst` | false-colour display of a single-channel image |
| `cv2.normalize` | `normalize(src, dst[, alpha[, beta[, norm_type[, dtype[, mask]]]]]) -> dst` | stretch values to 0–255 for display |

**Inputs and types.**

- Otsu's method in OpenCV works on 8-bit (and 16-bit) single-channel images only. The value you pass as `thresh` is ignored.
- `minMaxLoc` accepts 8-bit, 16-bit and floating-point single-channel arrays, so it works directly on temperature or depth data.
- `applyColorMap` needs an 8-bit input, so temperatures are normalized to 0–255 first. Do measurements on the original values, never on the coloured display image.

**In production.** Industrial cameras connect over standard interfaces such as GigE Vision and USB3 Vision, configured through the GenICam standard, usually with a vendor SDK rather than `cv2.VideoCapture` (59.5, 59.6). Results go to PLCs over industrial protocols and to databases and dashboards (60.4, 60.5).

## Where it fails

- **Uncontrolled lighting.** Daylight, reflections from hot steel, smoke and steam change the image constantly. *Instead:* engineer the lighting and shielding first (59.3, 59.4), then choose robust algorithms.
- **Calibration that drifts.** A camera knocked by a few millimetres, or warmed by the process, silently changes the pixel-to-mm scale. *Instead:* rigid mounts, reference targets in view, and regular re-calibration checks (41.6, 49.1).
- **Harsh environments.** Heat, dust, vibration and water damage cameras and dirty the lens. *Instead:* protective housings, air purging and cooling, chosen together with the camera (59.1).
- **Timing and motion.** A fast product blurs, or the image is taken at the wrong moment. *Instead:* short exposure, proper triggering, and line-scan cameras with encoders for continuous material (2.6, 59.5, 59.7).
- **Rare events with no examples.** A defect type that has never been seen cannot be learned from data, and rules may not cover it either. *Instead:* anomaly detection (55.6), operator feedback, and a safe default decision.
- **A wrong decision costs more than a missed image.** Stopping a mill line on a false alarm is expensive. *Instead:* measure false-alarm and miss rates on real plant data before go-live (58.4), and agree acceptable rates with the plant.

## ⚠️ Common mistakes

**1. Treating the camera as the system.** Budget and design time go to the camera, while lighting, mounting, triggering, PLC integration and the dashboard are left until site. Plan the whole chain (section 22).

**2. Measuring in pixels and reporting millimetres.** Without calibration, a pixel count is not a length. Record the scale, how it was obtained, and when.

**3. Leaving auto-exposure and auto white balance on.** The camera changes the image to look nice, and your thresholds stop working. Fix exposure, gain and white balance.

**4. Measuring on the colour-mapped display image.** False colours are for people. Compute temperatures and statistics on the original data.

**5. Testing only on good images.** A system tuned in the lab on clean samples fails in the plant. Collect images across shifts, seasons, product types and dirty-lens conditions.

**6. No tolerance in the decision.** `length == 1200` is never true. Compare against a tolerance agreed with the customer.

**7. Expecting AI to rescue a bad image.** Section 19's poor-lighting plate is hard for any method. Fix acquisition first.

### What a vision system is made of

Machine-vision engineering texts describe a vision system as a chain: illumination, optics, sensor and camera, interface, processing, and output to the controlling system. Each link limits the whole [1], [2]. The algorithms you learn in this course are one link.

### How many pixels does a feature need?

Sampling theory (Chapter 3.5) says a repeating pattern needs at least two samples per period to be represented at all. Practical inspection needs more: the smallest feature you must detect should cover several pixels, so that noise and blur do not hide it. Work out the scale before choosing a camera: field of view ÷ pixels = mm per pixel (section 5, Chapter 2.4), and compare it with the smallest defect and the required measurement tolerance [2].

### Sub-pixel measurement

Edges and centres can be located to a fraction of a pixel by fitting a model to the intensity profile, so measurement accuracy can be better than one pixel. This needs good contrast, low noise and a stable set-up: section 19 again (Chapters 22.5 and 49.2) [2].

### Why lighting changes the algorithm's job

The Otsu method used in the Code section picks the threshold that best separates two groups of gray levels [5]. With controlled lighting the crack and background form two well-separated groups, so any reasonable threshold works. With poor lighting the groups overlap and shift across the image, and no single global threshold can separate them. Better lighting turns a hard algorithm problem into an easy one.

### Camera characterization

How noisy is a camera, how sensitive, how linear? The EMVA 1288 standard defines how to measure and report these properties, so cameras from different makers can be compared fairly [6]. We use it in Module 2 (2.5) and Module 59.

## Exercises

### Exercise 1 (by hand)

A camera views a 600 mm wide field with a 1200-pixel-wide image. (a) How many mm does one pixel cover? (b) A billet spans 900 pixels. How long is it? (c) If the edge positions can be wrong by ±1 pixel each, roughly how large can the length error be?

<Solution>

(a) 600 mm ÷ 1200 px = **0.5 mm per pixel**.

(b) 900 px × 0.5 mm/px = **450 mm**.

(c) Each edge can be off by ±0.5 mm, so the length can be off by up to about **±1 mm**. To measure more precisely you need more pixels across the field (or a smaller field), or sub-pixel edge methods.

</Solution>

### Exercise 2 (coding)

Using the simulated thermal frame from the Code section, find the centre (mean x and mean y) of all pixels above 800 °C, and decide whether the hotspot lies inside a monitoring zone x 150–250, y 60–120.

<Solution>

```python
import numpy as np

H, W = 200, 320
yy, xx = np.mgrid[0:H, 0:W]
temp = 30 + 920 * np.exp(-(((xx - 200) / 45.0) ** 2 + ((yy - 90) / 30.0) ** 2))

ys, xs = np.nonzero(temp > 800)

inside zone
```

`np.nonzero` returns rows (y) first, then columns (x): the 1.2 rule again.

### Exercise 3 (by hand)

Design, as a list, a billet-ID reading station at a caster exit. Name every component of the **system** (not just the camera), and say which of the six questions (section 24) it answers.

<Solution>

A reasonable design:

1. **Camera** with a suitable resolution for the character size, in a **cooled, purged housing** (heat and dust).
2. **Lens** chosen for the working distance and field of view.
3. **Lighting** that gives clear contrast on the marking, and shields against glare from hot steel.
4. **Trigger** from a sensor or the PLC when a billet is in position.
5. **Industrial PC** running preprocessing and **OCR**.
6. **PLC link** to receive the expected ID and send the result.
7. **Database** to store image, read ID and time for traceability.
8. **Dashboard / alarm** for operators when a read fails or the ID does not match.

It mainly answers **WHAT?** (which billet is this: identification by reading its ID). With a check against the expected ID it also gives an **IS IT GOOD?** decision (correct billet or not).
