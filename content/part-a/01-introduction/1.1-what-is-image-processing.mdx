## 3. What is a pixel?

A pixel is the smallest individual element of a digital image.

For a grayscale image, one pixel might contain the number `128`. That number represents its **brightness**.

- `0` means **black**.
- `255` means **white**.
- `128` is approximately **gray**.

## 4. Why 255?

This is extremely important.

A normal 8-bit grayscale image uses **8 bits** for each pixel. One bit can contain `0` or `1`.

With 8 bits, we can represent 2⁸ = **256** different values. Those values are **0 → 255**: 256 possible intensity values.

<BitBuilder initial={128} />

<Flow direction="right" steps={["8-bit image", "256 possible values", "0 to 255"]} />

This is why you constantly see `255` in OpenCV.

## Code

First we write the logic ourselves, so nothing is hidden. Then we use OpenCV, which does the same thing faster and more safely.

### 1. The image as a NumPy array

```python
import numpy as np

img = np.array([[ 50,  80, 120],
                [ 90, 200, 230],
                [ 30, 160, 255]], dtype=np.uint8)

print(img.shape, img.dtype)
```

Output:

```text
(3, 3) uint8
```

- `np.array([...])` builds the grid of numbers, one inner list per row.
- `dtype=np.uint8` means *unsigned 8-bit integer*: whole numbers from 0 to 255. This is the type OpenCV uses for ordinary images.
- `img.shape` is `(rows, columns)`, which is `(height, width)`.

### 2. From scratch: a loop over every pixel

```python
inverted = np.zeros_like(img)          # an empty image of the same size and type
rows, cols = img.shape
for r in range(rows):                  # every row …
    for c in range(cols):              # … and every column in that row
        inverted[r, c] = 255 - img[r, c]
print(inverted)
```

Output:

```text
[[205 175 135]
 [165  55  25]
 [225  95   0]]
```

Dark pixels became bright and bright pixels became dark. Note the index order: `img[r, c]` is `img[row, column]`.

### 3. The same with NumPy, without a loop

NumPy applies a rule to every pixel at once. This is called *vectorization*.

```python
inverted = 255 - img                                              # invert
brighter = np.clip(img.astype(np.int16) + 50, 0, 255).astype(np.uint8)  # brighten, clipped
binary = np.where(img > 128, 255, 0).astype(np.uint8)             # threshold

print(brighter)
print(binary)
print("bright pixels:", np.count_nonzero(img > 128), "of", img.size)
print("mean:", img.mean())
```

Output:

```text
[[100 130 170]
 [140 250 255]
 [ 80 210 255]]
[[  0   0   0]
 [  0 255 255]
 [  0 255 255]]
bright pixels: 4 of 9
mean: 135.0
```

The brighten line needs care. `astype(np.int16)` moves the numbers into a bigger type, so 230 + 50 can really be 280. `np.clip(..., 0, 255)` then limits it to 255, and `astype(np.uint8)` returns to an image type.

Without that care, NumPy gets it wrong:

```python
print(img + 50)      # ⚠️ uint8 + 50 wraps around
```

Output:

```text
[[100 130 170]
 [140 250  24]
 [ 80 210  49]]
```

280 became 24 and 305 became 49. NumPy `uint8` arithmetic *wraps around* past 255, like a car odometer rolling over: 280 − 256 = 24.

### 4. The OpenCV way

```python
import cv2

inverted = cv2.bitwise_not(img)
brighter = cv2.add(img, 50)
retval, binary = cv2.threshold(img, 128, 255, cv2.THRESH_BINARY)

print(inverted)
print(brighter)
print(retval)
print(binary)
```

Output:

```text
[[205 175 135]
 [165  55  25]
 [225  95   0]]
[[100 130 170]
 [140 250 255]
 [ 80 210 255]]
128.0
[[  0   0   0]
 [  0 255 255]
 [  0 255 255]]
```

Every parameter:

- `cv2.bitwise_not(img)`: flips every bit of every pixel. For 8-bit images this equals 255 − p (see Go deeper for why).
- `cv2.add(img, 50)`: adds 50 to every pixel and **saturates**: results above 255 become 255, results below 0 become 0. This is the safe way to brighten.
- `cv2.threshold(img, 128, 255, cv2.THRESH_BINARY)`:
  - `img`: the source image.
  - `128`: the threshold. A pixel must be **strictly greater** than 128 to pass.
  - `255`: the value given to pixels that pass (OpenCV calls it `maxval`).
  - `cv2.THRESH_BINARY`: the rule "maxval if p > thresh, else 0".
  - It returns two things: the threshold that was used (`retval`, here `128.0`) and the result image.

### 5. On a real image file

Download [sample-scene.png](/images/sample-scene.png) into the folder you run Python from.

```python
import cv2

img = cv2.imread("sample-scene.png", cv2.IMREAD_GRAYSCALE)
if img is None:
    raise FileNotFoundError("Could not read sample-scene.png. Check the path.")

inverted = cv2.bitwise_not(img)
brighter = cv2.add(img, 80)
_, binary = cv2.threshold(img, 128, 255, cv2.THRESH_BINARY)

cv2.imwrite("inverted.png", inverted)
cv2.imwrite("brighter.png", brighter)
cv2.imwrite("binary.png", binary)
print("image size:", img.shape)
print("bright pixels:", cv2.countNonZero(binary), "of", img.size)
```

Output:

```text
image size: (200, 320)
bright pixels: 28106 of 64000
```

- `cv2.imread(path, cv2.IMREAD_GRAYSCALE)` loads the file as one 8-bit channel. Without the flag you get a 3-channel colour image.
- `if img is None` is not optional. When the file is missing, `imread` does **not** raise an error; it prints a warning and returns `None`.
- `cv2.imwrite(path, image)` saves the result. The file type comes from the extension (`.png`). It returns `True` on success.
- `cv2.countNonZero(binary)` counts the white pixels: information out, in one call.

## OpenCV API notes

Versions: OpenCV 4.13.0 (`opencv-python==4.13.0.92`). Signatures are copied from the installed library's own help text.

| Function | Python signature | Returns |
|---|---|---|
| `cv2.imread` | `imread(filename[, flags]) -> retval` | image array, or `None` if the file cannot be read |
| `cv2.imwrite` | `imwrite(filename, img[, params]) -> retval` | `True` / `False` |
| `cv2.bitwise_not` | `bitwise_not(src[, dst[, mask]]) -> dst` | inverted image |
| `cv2.add` | `add(src1, src2[, dst[, mask[, dtype]]]) -> dst` | saturated sum |
| `cv2.threshold` | `threshold(src, thresh, maxval, type[, dst]) -> retval, dst` | threshold used, result image |

**Inputs and types.**

- Images are NumPy arrays. Grayscale: shape `(height, width)`. Colour: `(height, width, 3)` in **B, G, R** order.
- The usual type is `uint8` (0 to 255). Industrial and thermal cameras often deliver `uint16`; OpenCV handles both, but check `img.dtype` before you assume 255 is "white".
- `cv2.threshold` accepts 8-bit, 16-bit and floating-point inputs, and processes each channel separately. Most of the time you give it one grayscale channel.
- `cv2.add` and `bitwise_not` work on any number of channels, each channel independently.

**Defaults.**

- `imread` without a flag loads a 3-channel colour image (`cv2.IMREAD_COLOR`).
- `mask` (in `add` and `bitwise_not`) is optional. When you give one, only pixels where the mask is non-zero are changed.

**Speed.**

- Never loop over pixels in Python for real work. In one test on a 1920×1080 image (a 2-core cloud machine, OpenCV 4.13.0), the Python loop took about 0.55 s; `255 - img` and `cv2.bitwise_not(img)` each took about 0.13 to 0.15 ms. That is roughly 4,000 times faster. Your numbers will differ; Chapter 7.7 shows how to measure.
- NumPy and OpenCV are similar for simple per-pixel maths. OpenCV is the safer default because it saturates.

## Where it fails

Pixel rules are powerful, but they have clear limits.

- **The same object gives different numbers.** Pixel values depend on lighting, exposure and the camera. A threshold tuned at noon can fail at night. *Instead:* control the lighting (59.3), normalise the image (Part B), or use adaptive methods (13.5).
- **It cannot recover what the camera never captured.** If a pixel is saturated at 255, the detail inside is gone. If the image is badly blurred, fine detail is lost. *Instead:* fix the camera, lens and exposure first (Module 2).
- **One pixel at a time ignores its neighbours.** Invert, brighten and threshold look at each pixel alone, so they cannot remove noise or find edges. *Instead:* use neighbourhood operations such as filters (Part C).
- **No understanding.** Pixel maths does not know what a "person" or a "billet" is. For objects that vary a lot in shape, pose and appearance, hand-written rules break. *Instead:* use learned models (Part J, deep learning). Image processing still matters there: it prepares the images.

## ⚠️ Common mistakes

**1. Overflow with NumPy `uint8` arithmetic.** `img + 50` wraps around: 230 + 50 gives 24, not 255. Bright areas suddenly turn dark. Use `cv2.add`, or convert to a bigger type, compute, then `np.clip` and convert back. The same happens with subtraction: with NumPy, 50 − 80 gives 226; `cv2.subtract` gives 0.

**2. Not checking `imread`.** A wrong path does not raise an error. `imread` returns `None`, and the crash happens later, far from the real cause. Always check `if img is None`.

**3. Mixing up x and y.** NumPy indexes `img[row, column]`, which is `img[y, x]`. And `img.shape` is `(height, width)`, not `(width, height)`.

**4. Assuming RGB order.** OpenCV loads colour images as **B, G, R**. Showing them with matplotlib (which expects R, G, B) swaps red and blue. Chapter 7.3 covers this.

**5. Thinking `b = img` makes a copy.** It does not. Both names point to the same pixels, so changing `b` changes `img`. Use `b = img.copy()`.

**6. Assuming 255 is always white.** A 16-bit image runs from 0 to 65535. Check `img.dtype` before you hard-code 255.

### An image as a function

Gonzalez and Woods define an image as a two-dimensional function f(x, y). Here x and y are coordinates in the plane, and the value of f at a point is the *intensity* (or gray level) there. When the coordinates and the intensity values are all finite, discrete numbers, the image is a **digital image** [1, Ch. 1].

Turning a continuous scene into a digital image takes two steps: *sampling* (choosing the grid of points) and *quantization* (rounding each brightness to a whole number). Chapters 3.1 and 3.2 cover them.

### Intensity levels

With k bits per pixel there are L = 2ᵏ intensity levels, from 0 to L − 1 [1, Sec. 2.4].

```text
k = 8   →  L = 256     →  0 … 255      (ordinary images)
k = 12  →  L = 4096    →  0 … 4095     (many industrial cameras)
k = 16  →  L = 65536   →  0 … 65535    (16-bit files, thermal data)
```

### Point operations

Every operation in the Code section (invert, brighten, multiply, threshold) is a **point operation**: the output pixel depends only on the input pixel at the same place. In Gonzalez and Woods' notation, s = T(r), where r is the input intensity and s the output [1, Ch. 3]. Szeliski calls these *point operators* and writes them as g(x) = h(f(x)) [2, Sec. 3.1].

- Invert is the image negative: s = L − 1 − r, which for 8-bit images is s = 255 − r [1, Sec. 3.2].
- Brighten is a *bias* (an added constant). Multiplying by a constant is a *gain*. Together they give g = a·f + b [2, Sec. 3.1].
- Threshold is a step function: s = 255 if r > t, else 0. OpenCV's `THRESH_BINARY` uses a strict "greater than" [3].

### Saturation and wrap-around, formally

OpenCV's `add` is defined as dst(I) = saturate(src1(I) + src2(I)) [3]. For 8-bit output, saturate(v) = min(max(round(v), 0), 255).

NumPy fixed-size integer types overflow instead [7]. For `uint8` the result is v mod 256: 280 mod 256 = 24. The OpenCV tutorial shows the same contrast with 250 + 10, which gives 255 in OpenCV and 4 in NumPy [6].

### Why bitwise NOT equals 255 − p

A `uint8` value is 8 bits. NOT flips every bit, so p and NOT p together have every bit set:

```text
p          = 0011 0010   (50)
NOT p      = 1100 1101   (205)
p + NOT p  = 1111 1111   (255)
```

So NOT p = 255 − p, for every 8-bit value.

### Pixel numbers are not amounts of light

In ordinary photos and screens, values are *gamma-encoded* (usually sRGB). The value 128 is not half the light of 255. Under the sRGB transfer function, 128 corresponds to about 22 % of the light of 255 [8]. This matters for measurement and blending. Chapter 11.3 explains gamma.

### Three levels of processing

Gonzalez and Woods describe a continuum [1, Ch. 1]:

- **Low-level:** image in, image out (noise reduction, contrast enhancement, sharpening). The Code section of this chapter.
- **Mid-level:** image in, attributes out (segmentation, edges, contours, object identity). The rod count in section 9 is an example.
- **High-level:** "making sense" of recognised objects, which shades into computer vision. Chapter 1.4 draws the line.

### A little history

Gonzalez and Woods trace early digital images to the Bartlane cable picture transmission system of the early 1920s, which sent newspaper pictures across the Atlantic and cut transmission time from more than a week to less than three hours. Computer image processing proper began in the early 1960s; a landmark was the processing of the Moon images sent back by the Ranger 7 probe in 1964 at the Jet Propulsion Laboratory [1, Ch. 1].

### Exercise 3 (coding)

A colleague brightens an image with `out = img + 100` and finds dark blotches where the image should be brightest. Explain the cause, then write two correct versions: one with OpenCV, one with NumPy only. Test both on the 3×3 image from the Code section.

<Solution>

**Cause:** `img` is `uint8`. Any result above 255 wraps around (for example 200 + 100 = 300 becomes 44), so the brightest pixels turn dark.

```python
import cv2
import numpy as np

img = np.array([[ 50,  80, 120],
                [ 90, 200, 230],
                [ 30, 160, 255]], dtype=np.uint8)

out_cv = cv2.add(img, 100)                                              # OpenCV: saturates
out_np = np.clip(img.astype(np.int16) + 100, 0, 255).astype(np.uint8)  # NumPy: widen, clip, narrow

print(out_cv)
print(np.array_equal(out_cv, out_np))
```

Output:

```text
[[150 180 220]
 [190 255 255]
 [130 255 255]]
True
```
