# 4.6 Metadata and watermarking

<Definition term="Metadata and watermarks">metadata is information stored **next to** the pixels (camera, time, orientation); a watermark is information hidden **in** the pixels themselves.</Definition>

A pixel array alone does not say when, where or how it was taken. For inspection that context is often as important as the image: which part, which camera, which settings, which result. This chapter covers where that information lives, how it gets lost, and how to mark or protect the images themselves.

## 1. An analogy

A parcel. **Metadata** is the label on the box: sender, date, contents. It is easy to read, easy to change and easy to lose if someone repacks the parcel. A **watermark** is a pattern woven into the cloth inside: hard to see, travels with the cloth, and survives repacking, unless the cloth is cut up badly enough.

## 2. What metadata files carry

<Chips items={["EXIF: camera, lens, exposure time, ISO/gain, date and time, orientation, GPS", "XMP: flexible XML (keywords, ratings, editing history)", "ICC profile: what the colour numbers mean", "PNG text chunks", "TIFF tags (resolution, description, custom tags)", "Video: timestamps, frame rate, codec (4.5)"]} />

**EXIF** (Exchangeable image file format) is the most common. It is stored inside JPEG, and also in PNG, WebP, AVIF and TIFF files, as a small TIFF-like table of numbered **tags**: tag 0x0112 is *Orientation*, 0x010E *ImageDescription*, and so on.

## 3. The orientation trap

Phones and some cameras don't rotate the pixels when you hold them sideways; they store the pixels as the sensor read them and set the **Orientation** tag (for example 6 = "rotate 90° clockwise to display").

`cv2.imread` **applies the orientation by default**. So the same file gives different shapes *(Code example 1)*:

| How it was read | Shape |
| --- | --- |
| `cv2.imread(path)` | (320, 200, 3): rotated |
| `cv2.imread(path, cv2.IMREAD_COLOR \| cv2.IMREAD_IGNORE_ORIENTATION)` | (200, 320, 3): as stored |

Another program may do the opposite. If a calibration (2.4) or ROI (3.4) was made on one and used on the other, every coordinate is wrong. Fixed industrial cameras rarely set this tag, but images from **phones** used for datasets or field inspections often do.

## 4. Reading and writing metadata in OpenCV

OpenCV 4.13 has `cv2.imreadWithMetadata` and `cv2.imwriteWithMetadata` (and `imdecodeWithMetadata` / `imencodeWithMetadata` for memory buffers). They return or take the raw EXIF bytes; OpenCV does not interpret the tags for you *(Code example 1)*.

**Plain `cv2.imwrite` writes no metadata.** Loading a phone photo and saving it again drops its EXIF, including the orientation, while the pixels have already been rotated: the saved file now looks right everywhere. Usually fine; but the camera, time and exposure information is gone.

## 6. Privacy

EXIF from phones can contain **GPS position**, device serial numbers and owner names. Strip metadata before sharing images outside the company (re-saving with plain `cv2.imwrite` does this). Pixels can also carry personal data: faces and licence plates in camera views need the same care as any personal data under your local rules.

## 7. Watermarks: information in the pixels

**Fragile** watermarks break at the smallest change: they prove an image was **not** modified. **Robust** watermarks survive compression, scaling and cropping: they prove where an image came from.

## 8. A fragile mark: the lowest bit

Every 8-bit value has 8 **bit planes** (3.2). Bit 7 carries the coarse picture; bit 0 changes the value by only 1 level and looks like noise. Replacing bit 0 with a message hides it with a maximum change of **1 level** (PSNR 51.1 dB) *(Code example 2)*:

| After hiding "LOT 4711" in bit 0 | Mark bits correct |
| --- | --- |
| Saved as PNG | 100.0 % |
| Saved as JPEG q95 | 50.2 % (random) |
| Saved as JPEG q75 | 50.0 % (random) |

JPEG rounds away exactly these smallest details (4.3): even at quality 95 the mark is completely gone. That makes LSB marks **fragile**: good for detecting changes, useless for proving origin after sharing.

## 10. A robust mark: spread spectrum

Instead of one bit, add a secret pattern of +3 / −3 to **every** pixel, generated from a key (a random seed). To check an image, correlate its fine texture with the pattern for that key: a high score means the mark is there *(Code example 3)*:

| Image | Score | × spread for wrong keys |
| --- | --- | --- |
| Original (no mark) | −0.00 | −0.1 |
| Marked (PSNR 38.6 dB) | 2.57 | 40.6 |
| Marked, JPEG q90 | 1.36 | 21.3 |
| Marked, JPEG q75 | 0.65 | 9.6 |
| Marked, JPEG q50 | 0.29 | 4.8 |

The mark weakens but stays clearly above the level of a wrong key, even at quality 50. Real robust schemes also survive scaling, rotation and cropping, which this simple one does not [2].

## 11. Proving an image is unchanged: hashes

For evidence and audits, a **cryptographic hash** (for example SHA-256) of the pixel bytes is simpler and stronger than a fragile watermark: change one bit of one pixel and the hash is completely different *(Code example 4)*. Store the hash in the database at capture time; anyone can re-compute it later. A **digital signature** over the hash also proves who created it.

## Mini exercise

**Q1.** A phone photo opens as 4000 × 3000 in one program and 3000 × 4000 in OpenCV. Why?

<Solution>

The file has an EXIF **orientation** tag. OpenCV applies it by default; the other program does not (or the reverse).

</Solution>

**Q2.** Hide a 1 in the LSB of the value 154, and a 0 in the LSB of 155. What is stored?

<Solution>

154 = 1001 1010 (bit 0 is 0) → 1001 1011 = **155**. 155 = 1001 1011 → 1001 1010 = **154**. Each changes by 1 level.

</Solution>

**Q3.** Why is a hash better than an LSB watermark for proving an image is unchanged?

<Solution>

The hash does not change the pixels at all, detects any change, and cannot be "repaired" by someone who rewrites the LSBs. It must be stored separately (database), which is also where the other context lives.

</Solution>

### 1. OpenCV: EXIF orientation and metadata

```python
import struct
import numpy as np
import cv2

def make_exif(orientation, description):
    """Minimal EXIF block (little-endian TIFF): ImageDescription (0x010E) and Orientation (0x0112)."""
    desc = description.encode("ascii") + b"\0"
    ifd = struct.pack("<H", 2)                                           # 2 entries
    ifd += struct.pack("<HHII", 0x010E, 2, len(desc), 8 + 2 + 2 * 12 + 4)  # ASCII text, stored after the IFD
    ifd += struct.pack("<HHIHH", 0x0112, 3, 1, orientation, 0)          # SHORT value, stored in the entry
    ifd += struct.pack("<I", 0)                                         # no further IFD
    return np.frombuffer(b"II*\0" + struct.pack("<I", 8) + ifd + desc, np.uint8)

img = cv2.imread("sample-color.png")                                     # 200 x 320
cv2.imwriteWithMetadata("tagged.jpg", img, [cv2.IMAGE_METADATA_EXIF], [make_exif(6, "line 3, camera 2")])

print("imread                 :", cv2.imread("tagged.jpg").shape)       # EXIF orientation applied
print("IMREAD_IGNORE_ORIENT.  :", cv2.imread("tagged.jpg", cv2.IMREAD_COLOR | cv2.IMREAD_IGNORE_ORIENTATION).shape)
pixels, types, chunks = cv2.imreadWithMetadata("tagged.jpg")
exif = chunks[0].tobytes()
print("metadata types         :", [int(t) for t in types], "(0 = EXIF),", len(exif), "bytes")
print("description in EXIF    :", exif[exif.find(b"line"):exif.find(b"\0", exif.find(b"line"))].decode())
cv2.imwrite("resaved.jpg", pixels)                                       # plain imwrite: metadata is gone
print("after plain imwrite    :", [int(t) for t in cv2.imreadWithMetadata("resaved.jpg")[1]], "(no metadata)")
```

Output:

```text
imread                 : (320, 200, 3)
IMREAD_IGNORE_ORIENT.  : (200, 320, 3)
metadata types         : [0] (0 = EXIF), 55 bytes
description in EXIF    : line 3, camera 2
after plain imwrite    : [] (no metadata)
```

- EXIF is a small TIFF structure: a byte-order mark (`II` = little-endian), then a table of 12-byte entries (tag, type, count, value or offset). `struct.pack("<HHII", …)` writes such fields in little-endian order.
- Type 2 = ASCII text, type 3 = 16-bit SHORT. Values that fit in 4 bytes are stored in the entry itself.
- In practice use a library (`piexif`, `exifread`, Pillow's `getexif()`) to read and edit tags; this example only shows what is inside.
- With OpenCV 4.13.0, EXIF writing worked for JPEG, PNG, WebP and AVIF; for TIFF it printed a warning and wrote none.

### 2. From scratch: a fragile LSB mark

```python
import numpy as np
import cv2

gray = cv2.imread("sample-scene.png", cv2.IMREAD_GRAYSCALE)
mark = np.zeros_like(gray)
cv2.putText(mark, "LOT 4711", (40, 120), cv2.FONT_HERSHEY_SIMPLEX, 1.6, 1, 4)     # 1 = bit set
stego = (gray & 0xFE) | mark                                                      # replace bit 0 with the mark

def recovered(img):
    return 100 * np.mean((img & 1) == mark)

print(f"max pixel change   : {np.abs(stego.astype(int) - gray).max()} level, PSNR {cv2.PSNR(gray, stego):.1f} dB")
print(f"after PNG          : {recovered(cv2.imdecode(cv2.imencode('.png', stego)[1], 0)):5.1f} % of mark bits correct")
for q in [95, 75]:
    dec = cv2.imdecode(cv2.imencode(".jpg", stego, [cv2.IMWRITE_JPEG_QUALITY, q])[1], 0)
    print(f"after JPEG q{q}     : {recovered(dec):5.1f} % of mark bits correct")
```

Output:

```text
max pixel change   : 1 level, PSNR 51.1 dB
after PNG          : 100.0 % of mark bits correct
after JPEG q95     :  50.2 % of mark bits correct
after JPEG q75     :  50.0 % of mark bits correct
```

- `gray & 0xFE` clears bit 0 (0xFE = 11111110); `| mark` sets it where the mark is 1.
- `cv2.putText(..., color=1, ...)` draws with value 1 so the text is directly a 0/1 mask.
- 50 % correct = coin flipping: no information left.

### 3. From scratch: a robust spread-spectrum mark

```python
import numpy as np
import cv2

gray = cv2.imread("sample-pinhole-scene.png", cv2.IMREAD_GRAYSCALE)
key = np.random.default_rng(seed=4711).choice([-1.0, 1.0], size=gray.shape)       # the secret pattern (the "key")
marked = np.clip(gray + 3 * key, 0, 255).astype(np.uint8)                          # add +-3 levels everywhere

def detect(img, k=key):
    f = img.astype(np.float32)
    detail = f - cv2.GaussianBlur(f, (5, 5), 0)                                    # drop the picture, keep fine texture
    return float(np.mean(detail * k))                                              # correlation with the key

others = [np.random.default_rng(seed=s).choice([-1.0, 1.0], size=gray.shape) for s in range(20)]
print(f"PSNR of the marked image: {cv2.PSNR(gray, marked):.1f} dB")
for name, img in [("original (no mark)", gray), ("marked", marked)] + [
        (f"marked, JPEG q{q}", cv2.imdecode(cv2.imencode(".jpg", marked, [cv2.IMWRITE_JPEG_QUALITY, q])[1], 0)) for q in [90, 75, 50]]:
    noise = np.std([detect(img, k) for k in others])                               # score spread for wrong keys
    print(f"{name:20s}: score {detect(img):5.2f}  ({detect(img) / noise:5.1f} x the wrong-key spread)")
```

Output:

```text
PSNR of the marked image: 38.6 dB
original (no mark)  : score -0.00  ( -0.1 x the wrong-key spread)
marked              : score  2.57  ( 40.6 x the wrong-key spread)
marked, JPEG q90    : score  1.36  ( 21.3 x the wrong-key spread)
marked, JPEG q75    : score  0.65  (  9.6 x the wrong-key spread)
marked, JPEG q50    : score  0.29  (  4.8 x the wrong-key spread)
```

- The key is a seed: only someone who knows 4711 can regenerate the pattern and check for it.
- Subtracting a blurred copy removes the picture (large, smooth structures), which would otherwise swamp the correlation.
- The "wrong-key spread" is how much the score varies by chance; a mark is detected when the score is many times that.

### 4. From scratch: a sidecar record with a hash

```python
import hashlib
import json
import numpy as np
import cv2

img = cv2.imread("sample-plate-good.png", cv2.IMREAD_GRAYSCALE)
cv2.imwrite("part_000123.png", img)
record = {
    "file": "part_000123.png",
    "time_utc": "2026-10-05T09:14:03.512Z",
    "line": 3, "camera_serial": "CAM-2-0042", "exposure_us": 800, "gain_db": 0.0,
    "lot": "4711", "recipe": "plate-v7", "result": "OK",
    "pixels_sha256": hashlib.sha256(img.tobytes()).hexdigest(),
}
with open("part_000123.json", "w") as f:
    json.dump(record, f, indent=2)

back = cv2.imread("part_000123.png", cv2.IMREAD_UNCHANGED)
saved = json.load(open("part_000123.json"))
print("pixels unchanged:", hashlib.sha256(back.tobytes()).hexdigest() == saved["pixels_sha256"])
back[10, 10] ^= 1                                       # change one bit of one pixel
print("after 1-bit edit:", hashlib.sha256(back.tobytes()).hexdigest() == saved["pixels_sha256"])
print("hash starts     :", saved["pixels_sha256"][:16])
```

Output:

```text
pixels unchanged: True
after 1-bit edit: False
hash starts     : 8145fb8703ee9ceb
```

- Hash the **pixels** (`img.tobytes()`), not the file: re-saving a PNG with another compression level changes the file bytes but not the pixels.
- For the hash to match, shape and dtype must match too: hash what you read with `IMREAD_UNCHANGED`.
- `^= 1` flips bit 0 (XOR).

## OpenCV API notes

**`cv2.imreadWithMetadata(path[, flags]) → img, types, chunks`**, **`cv2.imwriteWithMetadata(path, img, types, chunks[, params])`**, plus `imdecodeWithMetadata` / `imencodeWithMetadata`: `types` are `IMAGE_METADATA_*` constants (`IMAGE_METADATA_EXIF` = 0); `chunks` are `uint8` arrays with the raw bytes. Added in recent OpenCV versions (available in 4.13.0); older versions have no metadata API.

**`cv2.IMREAD_IGNORE_ORIENTATION`**: combine with `IMREAD_COLOR`, `IMREAD_GRAYSCALE` or `IMREAD_UNCHANGED` to skip EXIF rotation.

**Visible marks**: `cv2.putText`, `cv2.addWeighted(img, 1 − α, overlay, α, 0)` for a semi-transparent logo.

## Where it fails

- **Metadata is not trustworthy**: anyone can edit EXIF; camera clocks drift or are set wrong. Use synchronised clocks (NTP/PTP) and record in a controlled database.
- **Most tools strip or rewrite metadata**: image editors, messengers, web uploads, and plain `cv2.imwrite`.
- **Simple watermarks are easy to remove** by someone who knows the method; robust schemes are an arms race. Watermarks are not encryption.
- **Hashes prove "unchanged", not "true"**: an image can be faked before it is hashed. Hash at capture, on the inspection PC.

## ⚠️ Common mistakes

<Callout kind="mistake">

- **Calibrating on images rotated by EXIF** and running on unrotated frames (or the reverse).
- **Storing the only record of a result in EXIF** of a JPEG that will be re-saved.
- **Local time without time zone** in records: daylight-saving changes create duplicate or missing hours. Use UTC.
- **Sharing phone photos with GPS** in their metadata.
- **Hashing the file instead of the pixels**, then failing the check after a lossless re-save.

</Callout>

## 🔍 Go deeper

<GoDeeper>

### EXIF and its relatives

EXIF is defined by CIPA/JEITA (current version 3.0) [1]. It reuses TIFF's tag structure; JPEG stores it in an APP1 segment, PNG in an `eXIf` chunk. XMP (ISO 16684-1) stores metadata as XML and is common in professional tools.

### Robust watermarking

Cox, Kilian, Leighton and Shamoon's spread-spectrum watermarking embeds the mark in the most significant DCT coefficients of the image, so that removing it would visibly damage the image [2]. Modern schemes add synchronisation patterns to survive geometric changes. Steganography (hiding that a message exists at all) is a related but different goal.

### Content provenance

Standards such as C2PA attach cryptographically signed provenance records ("content credentials") to images and videos, recording how they were captured and edited. Some cameras sign images at capture.

</GoDeeper>
