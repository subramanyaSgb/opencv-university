# 8.8 G-API

<Definition term="G-API">OpenCV's graph API: you first describe a pipeline as a graph of operations on placeholder images, then compile and run it on real data. Because OpenCV sees the whole pipeline, it can choose backends, avoid storing intermediate images and run stages efficiently.</Definition>

Everything so far was **eager**: each `cv2.` call runs immediately and returns a full result image. G-API is a different style. It is not needed for most programs, but it explains how OpenCV can optimise whole pipelines, and it is the basis of OpenCV's streaming and inference pipelines.

## 1. An analogy

Cooking from a recipe vs cooking by improvising. Improvising (eager), you do one step, put the result in a bowl, look at the next step, use another bowl. With the whole recipe in front of you (graph), you can plan: chop while the water heats, reuse a bowl, skip a step whose result nobody uses. The food is the same; the kitchen is used better.

## 2. Describe, then run

- A `cv2.GMat` holds **no pixels**. It stands for "an image that will exist when the graph runs".
- `cv2.gapi.*` functions take and return placeholders (`GMat`, `GScalar`, `GOpaque`, `GArray`). Calling them only adds nodes to the graph.
- `GComputation` names the inputs and outputs. `apply()` compiles the graph for the input sizes and types (the first time) and runs it.

## 3. Why bother?

| Eager (classic cv2) | Graph (G-API) |
| --- | --- |
| Each step writes a full intermediate image to memory | The engine knows all steps; intermediates can be small or fused |
| You choose the device per call (UMat, cuda) | Choose a backend for the whole graph, per kernel package |
| Easy to debug: look at any intermediate | Intermediates are hidden unless you make them outputs |
| Best for exploration, small programs | Best for fixed, repeated pipelines (video, embedded) |

The main backends:

- **CPU (OpenCV)**: each operation calls the normal OpenCV function. Same results, little gain on its own.
- **Fluid**: processes the image **line by line**: each stage keeps only the few lines its kernel needs, so intermediate images never exist in full and data stays in the CPU cache. Very useful on embedded devices with little memory.
- **OpenCL**: runs the graph's operations on a GPU (8.6).
- **Inference backends** (OpenVINO, ONNX Runtime) run networks inside the graph (`cv2.gapi.infer`).

## 4. Memory: eager vs Fluid

Build an inspection graph and compare how much memory the intermediate results need.

<GraphLab caption="Pick stages and an image size. Eager keeps every intermediate image; Fluid keeps only a window of lines per stage. The code shows the G-API description of the graph you built." />

For a 5 MP image and all six stages, eager processing writes and reads five 5 MB intermediate images; Fluid needs about 13 lines (32 kB). The arithmetic is the same; the memory traffic is not, and memory traffic is often what limits speed (7.7).

## 5. Streaming mode

For video, G-API can compile a graph for streaming: a source (camera or file) feeds the graph, and stages run **pipelined** on consecutive frames, like the pipeline in 7.7, without writing the threading code yourself:

```text
comp = cv2.GComputation(cv2.GIn(g_in), cv2.GOut(g_out))
cc = comp.compileStreaming()
cc.setSource(cv2.gin(cv2.gapi.wip.make_capture_src("video.mp4")))
cc.start()
while True:
    ok, (out,) = cc.pull()
    if not ok:
        break
```

The same mechanism connects to inference: a graph can contain `cv2.gapi.infer` nodes that run a network on each frame or on regions found by earlier nodes (detect → crop → classify).

## 6. Industrial example

A smart camera with an ARM processor and 512 MB of RAM inspects 4096-pixel-wide line-scan blocks. The classic pipeline (difference to a golden template, blur, threshold, opening, count) allocated five full intermediate images per block and the camera ran out of memory at 4096 × 4096. The same pipeline described with G-API and compiled with the Fluid kernels processes each block line by line; peak memory for intermediates drops to tens of kilobytes, and the results are identical (example 2 checks this on a small image). The team kept the classic version for development and debugging, and uses the G-API version on the device.

## Code

Three examples: a deferred-execution graph from scratch, a G-API inspection graph checked against classic OpenCV (CPU and Fluid), and a custom operation.

### 1. From scratch: deferred execution

The idea of a graph API in 25 lines: nodes remember what to do; `run` evaluates them on demand.

```python
import numpy as np
import cv2

class Node:
    """A deferred operation: remembers what to do, does nothing until run()."""
    def __init__(self, fn, *inputs, name=""):
        self.fn, self.inputs, self.name = fn, inputs, name

def Input(name):
    return Node(None, name=name)

def run(node, feeds, log):
    if node.fn is None:                                        # a graph input: look up the real array
        return feeds[node.name]
    args = [run(i, feeds, log) for i in node.inputs]
    log.append(node.name)
    return node.fn(*args)

# Describe the pipeline (nothing is computed yet)
a, b = Input("ref"), Input("test")
diff = Node(lambda x, y: np.abs(x.astype(np.int16) - y.astype(np.int16)).astype(np.uint8), a, b, name="absdiff")
mask = Node(lambda d: (d > 40).astype(np.uint8) * 255, diff, name="threshold")
count = Node(lambda m: int(np.count_nonzero(m)), mask, name="count")
print("graph built; nothing computed yet")

ref = cv2.imread("sample-plate-good.png", cv2.IMREAD_GRAYSCALE)
test = ref.copy()
cv2.circle(test, (120, 80), 6, 0, -1)
log = []
print("count:", run(count, {"ref": ref, "test": test}, log), "| execution order:", log)
```

Output:

```text
graph built; nothing computed yet
count: 113 | execution order: ['absdiff', 'threshold', 'count']
```

- The graph is built before any image exists; the same graph can run on many image pairs.
- A real graph engine adds what this toy lacks: type and size checks at compile time, memory planning, backend selection, fused or line-based execution.

### 2. OpenCV: the inspection as a G-API graph

```python
import numpy as np
import cv2

ref = cv2.imread("sample-plate-good.png", cv2.IMREAD_GRAYSCALE)
test = ref.copy()
cv2.circle(test, (120, 80), 6, 0, -1)                          # a dark "defect"

# 1. Describe the graph: no pixels are processed here
g_ref, g_test = cv2.GMat(), cv2.GMat()
g_diff = cv2.gapi.absDiff(g_ref, g_test)
g_mask = cv2.gapi.threshold(g_diff, cv2.GScalar(40.0), cv2.GScalar(255.0), cv2.THRESH_BINARY)
g_clean = cv2.gapi.morphologyEx(g_mask, cv2.MORPH_OPEN, np.ones((3, 3), np.uint8))
g_count = cv2.gapi.countNonZero(g_clean)
comp = cv2.GComputation(cv2.GIn(g_ref, g_test), cv2.GOut(g_clean, g_count))

# 2. Run it on real images
mask, count = comp.apply(cv2.gin(ref, test))
print("outputs:", type(mask).__name__, mask.shape, "| count", count)

# 3. Same pipeline, classic OpenCV
m = cv2.threshold(cv2.absdiff(ref, test), 40, 255, cv2.THRESH_BINARY)[1]
m = cv2.morphologyEx(m, cv2.MORPH_OPEN, np.ones((3, 3), np.uint8))
print("classic count", cv2.countNonZero(m), "| identical masks:", np.array_equal(m, mask))

# 4. Run with the Fluid kernels where available
mask_f, count_f = comp.apply(cv2.gin(ref, test), args=cv2.gapi.compile_args(cv2.gapi.core.fluid.kernels()))
print("fluid count", count_f, "| identical:", np.array_equal(mask_f, mask))
```

Output:

```text
outputs: ndarray (200, 320) | count 109
classic count 109 | identical masks: True
fluid count 109 | identical: True
```

- Scalars in the graph are placeholders too: `threshold` takes `cv2.GScalar` values, not plain numbers.
- The opening removes 4 of the 113 thresholded pixels (the anti-aliased edge of the circle); G-API and classic OpenCV agree exactly.
- `compile_args` passes kernel packages and other options; kernels not in the given package come from the default CPU package.

### 3. OpenCV: a custom operation

Your own processing step can become a graph node: declare the operation (its inputs, outputs and output metadata) and provide a kernel that implements it.

```python
import numpy as np
import cv2

@cv2.gapi.op("course.Gamma", in_types=[cv2.GMat, float], out_types=[cv2.GMat])
class GGamma:
    @staticmethod
    def outMeta(desc, gamma):
        return desc                                            # same size and type as the input

@cv2.gapi.kernel(GGamma)
class GGammaImpl:
    @staticmethod
    def run(img, gamma):
        lut = (255 * (np.arange(256) / 255) ** gamma).round().astype(np.uint8)
        return cv2.LUT(img, lut)

g_in = cv2.GMat()
g_out = cv2.gapi.blur(GGamma.on(g_in, 0.5), (3, 3))
comp = cv2.GComputation(cv2.GIn(g_in), cv2.GOut(g_out))
img = np.array([[0, 64, 128, 255]] * 4, np.uint8)
out = comp.apply(cv2.gin(img), args=cv2.gapi.compile_args(cv2.gapi.kernels(GGammaImpl)))
print("gamma 0.5 then 3x3 blur, row 1:", out[1].tolist())
lut = (255 * (np.arange(256) / 255) ** 0.5).round().astype(np.uint8)
print("classic:", cv2.blur(cv2.LUT(img, lut), (3, 3))[1].tolist())
```

Output:

```text
gamma 0.5 then 3x3 blur, row 1: [85, 103, 188, 206]
classic: [85, 103, 188, 206]
```

- `outMeta` tells the graph the output's size and type before any data exists; that is how G-API checks and plans the whole graph at compile time.
- The kernel is Python here (convenient, slower); in C++ the same mechanism adds optimised kernels for any backend.

## OpenCV API notes

**Placeholders**: `cv2.GMat()`, `cv2.GScalar(value)`, `cv2.GOpaque`, `cv2.GArray`; **operations**: `cv2.gapi.*` (core: `add`, `absDiff`, `threshold`, `resize`, `countNonZero` …; imgproc: `blur`, `gaussianBlur`, `Canny`, `morphologyEx`, `BGR2Gray` …).

**Graph and run**: `cv2.GComputation(cv2.GIn(...), cv2.GOut(...))`, `comp.apply(cv2.gin(...), args=cv2.gapi.compile_args(...))`, `comp.compileStreaming()` → `setSource`, `start`, `pull`, `stop`.

**Kernel packages**: `cv2.gapi.core.cpu.kernels()`, `cv2.gapi.core.fluid.kernels()`, `cv2.gapi.core.ocl.kernels()`, `cv2.gapi.combine(pkg1, pkg2)`, `cv2.gapi.kernels(MyImpl, …)` for custom kernels.

**Custom operations**: `@cv2.gapi.op(name, in_types, out_types)` with `outMeta`, `@cv2.gapi.kernel(Op)` with `run`.

**Inference**: `cv2.gapi.infer`, `cv2.gapi.onnx.params`, `cv2.gapi.ov.params` (OpenVINO), `cv2.gapi.networks(...)`.

## Where it fails

- **Debugging**: intermediate images are not visible unless added as outputs.
- **Coverage**: not every OpenCV function exists as a G-API operation; missing ones need custom kernels.
- **Python overhead**: custom kernels written in Python run at Python speed and break line-based execution.
- **Learning curve and documentation**: fewer examples than classic OpenCV, especially for Python.
- **Small, one-off scripts**: the graph setup is not worth it.

## ⚠️ Common mistakes

<Callout kind="mistake">

- **Expecting a GMat to contain pixels** (printing it, indexing it).
- **Passing plain numbers where a GScalar is expected** (`threshold`).
- **Rebuilding the GComputation for every frame** instead of building it once and applying it many times.
- **Assuming Fluid makes everything faster**: it saves memory traffic; the gain depends on the pipeline and the CPU.
- **Forgetting outMeta** (or returning the wrong metadata) in a custom operation.

</Callout>

## 🔍 Go deeper

<GoDeeper>

### Compilation

`apply()` on a new input format compiles the graph: it checks every node's input and output metadata (from `outMeta`), selects a kernel for each node from the kernel packages (custom packages first), partitions the graph into "islands" per backend, and plans memory. The compiled object is cached for the same input metadata, so later `apply()` calls only execute [1].

### Line-based processing

Fluid kernels declare a window (for example 5 lines for a 5 × 5 filter) and a border. The executor runs each island top to bottom: it produces one output line of the last stage by pulling just enough lines through every earlier stage, keeping circular line buffers between stages. Intermediate data stays in the L1/L2 cache, which is why line-based pipelines are popular on embedded vision processors [1].

</GoDeeper>
