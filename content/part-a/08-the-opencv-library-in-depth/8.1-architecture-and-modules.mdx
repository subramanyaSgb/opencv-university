# 8.1 Architecture and modules

<Definition term="OpenCV architecture">the way the library is built in layers (Python on top, C++ in the middle, optimised code and third-party libraries underneath) and split into modules, each responsible for one kind of task.</Definition>

Module 7 used OpenCV as a black box: `cv2.something(...)`. This module opens the box. Knowing how the library is organised tells you where to look in the documentation, which package to install, why a function is "missing", and where speed comes from.

## 1. An analogy

A large hardware store. You walk in through one entrance (`import cv2`), but the store has departments: fasteners, paint, electrical, garden. Each department has its own shelves and specialists. Behind the shop floor there is a warehouse and suppliers you never see. Some special items are not in the main store at all: they are in the annex next door (contrib), and you only find them if the annex is open (the right package is installed).

## 2. Four layers

- **Python bindings** (`cv2`): generated automatically from the C++ headers. A call like `cv2.GaussianBlur(img, (5, 5), 0)` wraps the NumPy array as a `cv::Mat` (no copy when possible), calls C++, and wraps the result as a NumPy array (8.3).
- **C++ API**: the real implementation. Everything is in the namespace `cv`; images are `cv::Mat` (8.2).
- **Optimised kernels**: the same function has several code paths: plain C++, SIMD versions chosen at run time for your CPU (SSE4, AVX2, AVX-512, NEON on ARM), a parallel loop split over cores, and sometimes Intel IPP (a bundled subset called IPPICV).
- **Third-party libraries**: image formats (libjpeg-turbo, libpng, libtiff, libwebp, OpenJPEG, OpenEXR), video (FFmpeg, GStreamer, Media Foundation on Windows), deep-learning model files (protobuf), linear algebra (LAPACK/OpenBLAS).

This is why a single Python line can be fast: almost no time is spent in Python; the work happens in compiled, vectorised, multi-threaded C++.

## 3. The main modules

OpenCV's main repository is split into modules. In C++ each is a library (`opencv_imgproc`) with a header (`opencv2/imgproc.hpp`); in Python they are all merged into `cv2`, with a few sub-namespaces (`cv2.aruco`, `cv2.dnn`, `cv2.ml`, `cv2.cuda`, `cv2.ocl`, `cv2.gapi`).

| Module | What it does | Typical functions | Course chapters |

| **imgproc** | Image processing: filters, geometry, colour, histograms, thresholds, contours, drawing | `GaussianBlur`, `warpAffine`, `cvtColor`, `threshold`, `findContours`, `line` | Parts B–D |

## 4. Main repository vs opencv_contrib

OpenCV is developed in two repositories:

- **opencv** (main): stable, well-tested modules listed above.
- **opencv_contrib**: extra modules: newer algorithms, specialised topics, or code with patent or licence restrictions. Examples: `xfeatures2d` (SURF, and other descriptors), `ximgproc` (guided filter, edge-aware filters, thinning), `tracking` (extra trackers), `face`, `text`, `freetype` (TrueType text drawing), `cudaimgproc` and the other CUDA modules.

Algorithms move between them over time: SIFT moved from contrib to main in 4.4.0 after its patent expired; ArUco moved to `objdetect` in 4.7.0. Chapter 8.4 covers contrib in detail.

The pip packages map onto this:

| pip package | Main modules | contrib | GUI (highgui windows) |
| --- | --- | --- | --- |
| `opencv-python` | yes | no | yes |
| `opencv-python-headless` | yes | no | no (servers, Docker) |
| `opencv-contrib-python` | yes | yes | yes |
| `opencv-contrib-python-headless` | yes | yes | no |

Install exactly **one** of them (7.1). Two installed at once overwrite each other's `cv2` folder.

## 5. How a call travels through the layers

Follow `cv2.GaussianBlur(img, (5, 5), 0)` on a 2448 × 2048 uint8 image:

Practical consequences:

- **One big call beats many small calls.** Each Python → C++ crossing costs microseconds; a loop over pixels in Python calls the binding millions of times (6.1).
- **Data types matter.** Many kernels have fast paths only for uint8 and float32; float64 or odd channel counts may take a slower generic path.
- **Memory layout matters.** A non-contiguous array (a slice with a step, 6.3) may be copied before the call.

## 6. Build options: what is inside your cv2

OpenCV is compiled with options (CMake flags) that decide which modules, third-party libraries and accelerations are included. The pip wheels are built by the opencv-python project with a fixed set of options; a custom build (8.5) can add CUDA, GStreamer, TBB or contrib modules.

`cv2.getBuildInformation()` prints the whole configuration. The lines worth reading:

| Line | Tells you |
| --- | --- |
| `To be built:` | The modules in this build |
| `Non-free algorithms:` | Whether patented contrib code (SURF) is included |
| `GUI:` | Window backend (NONE in headless builds) |
| `Video I/O:` | FFmpeg, GStreamer, camera backends |
| `CPU/HW features: Baseline / Dispatched` | SIMD always used vs chosen at run time |
| `Parallel framework:` | pthreads, TBB, OpenMP, Concurrency … |
| `NVIDIA CUDA:` / `OpenCL:` | GPU support (8.5, 8.6) |

When a colleague says "it works on my PC", compare the two build information printouts first.

## 7. Industrial example

A vision PC on a packaging line uses ArUco markers to locate the tray and a small ONNX model to classify labels. The team pins `opencv-python-headless==4.13.0.92` in `requirements.txt` (no GUI needed on the line, operator screens are a separate web app). A developer's notebook uses `opencv-contrib-python` for experiments with the guided filter. Before deploying, the build check below runs in the CI pipeline and fails if `cv2.aruco` or `cv2.dnn` is missing, or if the version differs from the pinned one. This catches a wrong package in the Docker image before it reaches the line.

## Mini exercise

**Q1.** Which module holds `cv2.findContours`? And `cv2.imwrite`?

<Solution>

`findContours` is **imgproc**; `imwrite` is **imgcodecs**.

</Solution>

**Q2.** `cv2.ximgproc` raises `AttributeError`. Why, and what fixes it?

<Solution>

ximgproc is an **opencv_contrib** module; the installed package (for example `opencv-python`) does not contain it. Uninstall it and install the matching `opencv-contrib-python` version (only one OpenCV package at a time).

</Solution>

**Q3.** Why is `cv2.GaussianBlur` on a whole image much faster than a Python loop that averages each pixel's neighbours?

<Solution>

The OpenCV call crosses into C++ once and runs vectorised (SIMD), multi-threaded code. The Python loop runs the interpreter for every pixel.

</Solution>

### 1. What is in my cv2?

NumPy is not needed for the build check itself, but every script in the course starts with the same two imports.

```python
import numpy as np
import cv2

info = cv2.getBuildInformation()
line = next(l for l in info.splitlines() if "To be built:" in l)
built = line.split(":", 1)[1].split()
print("OpenCV", cv2.__version__, "|", len(built), "modules built")
print(" ".join(built))
for name in ["aruco", "dnn", "ml", "cuda", "ocl", "gapi", "xfeatures2d", "ximgproc", "freetype"]:
    print(f"cv2.{name:12s} {'yes' if hasattr(cv2, name) else 'no'}")
nonfree = next(l for l in info.splitlines() if "Non-free algorithms" in l).split(":")[1].strip()
print("non-free algorithms:", nonfree)
```

### 2. One pipeline, several modules

A small inspection that uses core, imgproc, imgcodecs and objdetect, all through `cv2`:

```python
import numpy as np
import cv2

img = np.zeros((60, 80), np.uint8)
cv2.rectangle(img, (20, 15), (59, 44), 200, -1)              # imgproc (drawing)
ok, buf = cv2.imencode(".png", img)                          # imgcodecs: to PNG bytes in memory
back = cv2.imdecode(buf, cv2.IMREAD_GRAYSCALE)               # imgcodecs: and back
blur = cv2.GaussianBlur(back, (5, 5), 0)                     # imgproc
_, bw = cv2.threshold(blur, 100, 255, cv2.THRESH_BINARY)     # imgproc
contours, _ = cv2.findContours(bw, cv2.RETR_EXTERNAL, cv2.CHAIN_APPROX_SIMPLE)   # imgproc
x, y, w, h = cv2.boundingRect(contours[0])                   # imgproc
mean = cv2.mean(back)[0]                                     # core
print(f"PNG round trip identical: {np.array_equal(img, back)} | contours {len(contours)} | box {x},{y},{w},{h} | mean {mean:.1f}")

d = cv2.aruco.getPredefinedDictionary(cv2.aruco.DICT_4X4_50) # objdetect (aruco sub-namespace)
marker = cv2.aruco.generateImageMarker(d, 7, 60)              # marker id 7, 60 x 60 pixels
canvas = cv2.copyMakeBorder(marker, 20, 20, 20, 20, cv2.BORDER_CONSTANT, value=255)   # core: white quiet zone
corners, ids, _ = cv2.aruco.ArucoDetector(d).detectMarkers(canvas)
print("aruco ids:", ids.ravel().tolist(), "| first corner:", corners[0][0][0].tolist())
```

Output:

```text
PNG round trip identical: True | contours 1 | box 20,15,40,30 | mean 50.0
aruco ids: [7] | first corner: [20.0, 20.0]
```

- The mean is exact: 40 × 30 pixels of 200 in 80 × 60 → 200 · 1200 / 4800 = 50.
- The ArUco detector needs a white border around the marker (the "quiet zone"); without `copyMakeBorder` it finds nothing.

### 3. Acceleration on this machine

```python
import numpy as np
import cv2

info = cv2.getBuildInformation().splitlines()
for key in ["Baseline:", "Parallel framework:"]:
    print(next(l.strip() for l in info if key in l))
print("CPU features at run time:", cv2.getCPUFeaturesLine())
print("optimised code on:", cv2.useOptimized(), "| IPP on:", cv2.ipp.useIPP())
print("CPUs:", cv2.getNumberOfCPUs(), "| OpenCV threads:", cv2.getNumThreads())
```

Typical output on our Linux test machine (other CPUs and the Windows wheels print different lines):

```text
Baseline:                    SSE SSE2 SSE3
Parallel framework:            pthreads
CPU features at run time: SSE SSE2 SSE3 *SSE4.1 *SSE4.2 *AVX *FP16 *AVX2 *AVX512-SKX
optimised code on: True | IPP on: True
CPUs: 2 | OpenCV threads: 2
```

- **Baseline** features are compiled into every function; features marked `*` are **dispatched**: extra code paths chosen at run time if the CPU supports them. A wheel built for SSE3 still uses AVX2 on a modern CPU.
- `cv2.setUseOptimized(False)` switches the optimised paths off (useful only to compare results or speed).

## OpenCV API notes

**Build and version**: `cv2.__version__`, `cv2.getVersionString()`, `cv2.getBuildInformation()`.

**CPU and threads**: `cv2.getCPUFeaturesLine()`, `cv2.checkHardwareSupport(feature_id)`, `cv2.getNumberOfCPUs()`, `cv2.setNumThreads(n)`, `cv2.getNumThreads()`.

**Optimisation switches**: `cv2.setUseOptimized(bool)` / `cv2.useOptimized()`; `cv2.ipp.setUseIPP(bool)` / `cv2.ipp.useIPP()`.

**Python sub-namespaces**: `cv2.aruco`, `cv2.dnn`, `cv2.ml`, `cv2.cuda`, `cv2.ocl`, `cv2.gapi`, `cv2.fisheye`, `cv2.barcode`; with contrib also `cv2.xfeatures2d`, `cv2.ximgproc`, `cv2.freetype` and others.

**Documentation**: `https://docs.opencv.org/4.13.0/` → "Modules" lists every module, main and contrib; each function page names its module and header.

## Where it fails

- **Docs vs installed package**: the online docs include contrib modules; a function from the docs may not exist in your package.
- **Version drift**: functions move (ArUco API changed in 4.7.0: `ArucoDetector` instead of `detectMarkers` as a free function), so old tutorials fail on new versions.
- **Python names differ from C++**: overloaded C++ functions or classes with factories appear as `cv2.SIFT_create()` or `cv2.SIFT.create()`; check `help(cv2.xxx)`.
- **Build information is static**: it shows what was compiled in, not whether the hardware (GPU, camera backend) actually works on this PC.

## ⚠️ Common mistakes

<Callout kind="mistake">

- **Installing two OpenCV packages** (for example `opencv-python` and `opencv-contrib-python`): they overwrite each other.
- **Assuming `hasattr(cv2, "cuda")` means a GPU is used**: the namespace exists in every wheel.
- **Following a tutorial for another major version** without checking the module and function names.
- **Looking for SURF in the pip wheels**: it is non-free and not included in the pip packages; use ORB, SIFT or AKAZE.

</Callout>

## 🔍 Go deeper

<GoDeeper>

### Where the bindings come from

The Python (and Java, JavaScript) bindings are generated: a script parses the C++ headers and reads export macros such as `CV_EXPORTS_W` (export to wrappers) and `CV_WRAP` on methods. `CV_OUT` / `CV_IN_OUT` mark output arguments, which in Python become return values. That is why `cv2.threshold` returns `(retval, dst)` while in C++ `dst` is a parameter [3].

### Universal intrinsics and HAL

OpenCV writes SIMD code once using "universal intrinsics" (types like `v_uint8` and operations like `v_add`) that compile to SSE/AVX on x86, NEON on ARM, RVV on RISC-V and others. A Hardware Acceleration Layer (HAL) lets vendors plug in their own optimised implementations (IPP on Intel, Carotene on ARM) for selected functions [1].

### Algorithm hints

Recent 4.x builds print an `Algorithm Hint` line (here `ALGO_HINT_ACCURATE`), and `cv2.ALGO_HINT_DEFAULT`, `cv2.ALGO_HINT_ACCURATE` and `cv2.ALGO_HINT_APPROX` exist in Python. Some functions accept a hint to allow a faster, approximate implementation (for example a fixed-point GaussianBlur). By default results stay bit-exact between platforms for most functions. ### Exercise 2 (coding)

Write a function `require(features)` that raises a clear error at program start if the installed OpenCV is not version 4.13.x or misses any of the named sub-namespaces. Test it with `["aruco", "dnn"]` (passes) and `["ximgproc"]` (fails with the pinned headless package).

<Solution>

```python
import numpy as np
import cv2

def require(features):
    if not cv2.__version__.startswith("4.13."):
        raise RuntimeError(f"need OpenCV 4.13.x, found {cv2.__version__}")
    missing = [f for f in features if not hasattr(cv2, f)]
    if missing:
        raise RuntimeError(f"missing cv2 modules: {missing} (install the matching opencv-contrib-python?)")
    return True

print(require(["aruco", "dnn"]))
try:
    require(["ximgproc"])
except RuntimeError as e:
    print("error:", e)
```

Output:

```text
True
error: missing cv2 modules: ['ximgproc'] (install the matching opencv-contrib-python?)
```

</Solution>
