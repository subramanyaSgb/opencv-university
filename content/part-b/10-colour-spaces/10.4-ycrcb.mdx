# 10.4 YCrCb

<Definition term="YCrCb">a colour space that stores a pixel as **Y**, the luma (a weighted brightness), and two colour differences: **Cr** (red minus luma) and **Cb** (blue minus luma). It is the colour space of digital video, JPEG and most camera streams.</Definition>

You met YCrCb in 4.3: JPEG converts to it and stores the colour channels at half resolution. This chapter looks at the space itself: what the three numbers mean, why separating brightness from colour is so useful, and how to use it in OpenCV.

## 1. An analogy

A black-and-white photograph plus a separate, slightly blurry colouring layer. The photograph holds all the fine detail (edges, texture, text). The colour layer only says "this area is reddish, that one bluish". Our eyes judge detail mostly from brightness, so a soft colour layer looks perfectly fine on top of a sharp photograph.

## 2. The three channels

<Flow

- **Y** uses the same weights as `COLOR_BGR2GRAY` (10.5): green counts most, like the eye (9.1).
- **Cr** and **Cb** are signed colour differences, shifted by **128** so they fit in 0…255. Any grey (R = G = B) has Cr = Cb = 128.
- OpenCV's order is **Y, Cr, Cb** (`COLOR_BGR2YCrCb`); many other libraries and video formats use Y, Cb, Cr ("YCbCr", "YUV"). Same information, different channel order and sometimes different ranges (video "limited range" 16–235).

| Colour | BGR | Y, Cr, Cb |
| --- | --- | --- |
| red | (0, 0, 255) | 76, 255, 85 |
| green | (0, 255, 0) | 150, 21, 43 |
| blue | (255, 0, 0) | 29, 107, 255 |
| grey | (128, 128, 128) | 128, 128, 128 |
| orange | (40, 150, 255) | 169, 189, 55 |

<YccLab caption="Mix a colour with B, G, R; see Y, Cr, Cb and the point in the Cr–Cb plane. The tiles show the colour split into its luma and chroma parts. A shadow moves the point towards the neutral centre." />

Things to try: look at the "Y only" tile: it is the colour's grey version. "Cr, Cb only" shows the colour at a fixed medium brightness. Darken with the shadow slider: the point slides towards the centre along the same ray.

## 3. Why video and JPEG use it

- **Chroma subsampling**: store Cr and Cb at half width and half height (**4:2:0**): half the data of full RGB, with little visible loss because colour detail matters less to the eye (4.3, 4.5).
- **Black-and-white compatibility**: historically TV could show Y alone.
- **Compression**: Y, Cr, Cb are much less correlated than R, G, B, so each compresses better.

Example 2 below quantifies it: blurring the colour channels hardly changes the grey-level image; blurring luma damages it.

## 4. Using YCrCb in processing

| Task | How |
| --- | --- |
| Adjust brightness or contrast without colour shifts | process Y only (CLAHE on Y, 12.3), merge back |
| Denoise colour noise without blurring detail | blur Cr and Cb, leave Y |
| Detect strongly coloured regions | distance of (Cr, Cb) from (128, 128) |
| Skin detection (classic method) | box in the Cr–Cb plane (Chai & Ngan: Cr 133–173, Cb 77–127) [1] |
| Read camera streams | many cameras deliver YUV formats (NV12, YUY2); `cv2.cvtColor` with `COLOR_YUV2BGR_NV12` etc. |

**Shading**: a shadow lowers Y and pulls Cr and Cb towards 128 in proportion. Cr and Cb are therefore **not** brightness-invariant on their own (unlike hue or chromaticity), but the **direction** of (Cr − 128, Cb − 128) is.

## 5. Industrial example

A camera inspecting printed packaging delivers an NV12 (YUV 4:2:0) stream. Print defects that matter (missing text, smears, streaks) are visible in Y alone, at full resolution. The inspection therefore runs its detail checks on Y, which is a free byproduct of the stream (no colour conversion at all for those checks), and uses the half-resolution Cr, Cb planes only for a coarse colour-registration check. This halves the data to process and avoids converting every frame to BGR.

**Q1.** What are Y, Cr, Cb of a grey pixel (90, 90, 90)?

<Solution>

Y = 90 (weights sum to 1); R − Y = B − Y = 0 → Cr = Cb = **128**: (90, 128, 128).

</Solution>

**Q2.** How many bytes does a 1920 × 1080 frame need in 4:2:0 compared with full BGR?

Y: 1920 · 1080 = 2 073 600; Cr and Cb each 960 · 540 = 518 400 → total **3 110 400 B** vs 6 220 800 B for BGR: **half**.

## Code

Two examples: YCrCb from scratch, and what happens when colour or luma loses resolution.

### 1. From scratch: BGR to YCrCb

```python
import numpy as np
import cv2

def bgr_to_ycrcb(img):
    """From scratch: ITU-R BT.601 luma, colour differences scaled and offset by 128 (OpenCV's convention)."""
    f = img.astype(np.float64)
    y = 0.299 * f[..., 2] + 0.587 * f[..., 1] + 0.114 * f[..., 0]
    cr = (f[..., 2] - y) * 0.713 + 128
    cb = (f[..., 0] - y) * 0.564 + 128
    return np.clip(np.round(np.stack([y, cr, cb], axis=-1)), 0, 255).astype(np.uint8)

img = cv2.imread("sample-color.png")
ours, cv = bgr_to_ycrcb(img).astype(int), cv2.cvtColor(img, cv2.COLOR_BGR2YCrCb).astype(int)
print("max |ours - cv2| per channel Y, Cr, Cb:", np.abs(ours - cv).max(axis=(0, 1)).tolist())
for name, y, x in [("orange", 175, 100), ("red", 95, 70), ("grey bg", 5, 5)]:
    print(f"{name:7s} BGR {img[y, x].tolist()} -> YCrCb {cv[y, x].tolist()}")
```

Output:

```text
max |ours - cv2| per channel Y, Cr, Cb: [0, 1, 0]
orange  BGR [40, 150, 255] -> YCrCb [169, 189, 55]
red     BGR [0, 0, 220] -> YCrCb [66, 238, 91]
grey bg BGR [40, 32, 28] -> YCrCb [32, 125, 133]
```

- OpenCV's 8-bit path uses fixed-point arithmetic, so a value can differ by 1 from the floating-point formula.
- The dark background is nearly neutral: Cr and Cb close to 128.

### 2. OpenCV: half-resolution colour vs half-resolution luma

```python
import numpy as np
import cv2

img = cv2.imread("sample-color.png")
ycc = cv2.cvtColor(img, cv2.COLOR_BGR2YCrCb)
h, w = img.shape[:2]

def halve(ch):                                   # store at half width and height, then scale back up
    small = cv2.resize(ch, (w // 2, h // 2), interpolation=cv2.INTER_AREA)
    return cv2.resize(small, (w, h), interpolation=cv2.INTER_LINEAR)

y, cr, cb = cv2.split(ycc)
chroma_420 = cv2.cvtColor(cv2.merge([y, halve(cr), halve(cb)]), cv2.COLOR_YCrCb2BGR)
luma_420 = cv2.cvtColor(cv2.merge([halve(y), cr, cb]), cv2.COLOR_YCrCb2BGR)
for name, out in [("Cr, Cb at half resolution (4:2:0)", chroma_420), ("Y at half resolution instead", luma_420)]:
    print(f"{name:34s}: PSNR {cv2.PSNR(img, out):5.1f} dB | grey-level error of the result {cv2.PSNR(cv2.cvtColor(img, cv2.COLOR_BGR2GRAY), cv2.cvtColor(out, cv2.COLOR_BGR2GRAY)):5.1f} dB")
print("data: full 3 planes", 3 * h * w, "bytes | 4:2:0", h * w + 2 * (h // 2) * (w // 2), "bytes")
```

Output:

```text
Cr, Cb at half resolution (4:2:0) : PSNR  31.5 dB | grey-level error of the result  63.8 dB
Y at half resolution instead      : PSNR  31.7 dB | grey-level error of the result  31.7 dB
data: full 3 planes 192000 bytes | 4:2:0 96000 bytes
```

- Both versions lose about the same amount measured on all three BGR channels (PSNR ≈ 31.5 dB), but the 4:2:0 version keeps the grey-level image essentially perfect (63.8 dB): the losses are only in colour, where the eye and most inspections care least.
- Half the data for the same perceived quality: that is why every video codec does it (4.5).

## OpenCV API notes

**Conversion**: `cv2.COLOR_BGR2YCrCb`, `COLOR_YCrCb2BGR` (order Y, Cr, Cb; full range 0–255; BT.601 weights). `COLOR_BGR2YUV`, `COLOR_YUV2BGR` (Y, U = Cb-like, V = Cr-like).

**Camera and video formats**: `COLOR_YUV2BGR_NV12`, `_NV21`, `_I420`, `_YV12`, `COLOR_YUV2BGR_YUY2`, `_UYVY`; `COLOR_BGR2YUV_I420` for encoding. For these, the input is a single-channel array with the planes stacked (height × 3/2 for 4:2:0).

**Per-channel processing**: `cv2.split` / `cv2.merge`, or process `ycc[..., 0]` in place.

## Where it fails

- **Not perceptually uniform**: equal steps in Cr, Cb are not equal colour differences (use Lab).
- **Range conventions**: full range (0–255) vs limited range (Y 16–235, chroma 16–240) and BT.601 vs BT.709 weights; mixing them shifts colours and contrast.
- **Brightness dependence**: Cr and Cb shrink in shadows.
- **Fine colour detail** (thin coloured lines, colour-coded text) is lost by 4:2:0 subsampling.

## ⚠️ Common mistakes

<Callout kind="mistake">

- **Assuming YCrCb order** for data that is YCbCr (or YUV), or the reverse.
- **Ignoring limited-range video**: blacks at 16 and whites at 235 look washed out if treated as full range.
- **Measuring thin coloured features** in 4:2:0 streams.
- **Equalising all three channels** instead of only Y (colours shift).

</Callout>

## 🔍 Go deeper

### Where the constants come from

ITU-R BT.601 defines luma as 0.299 R′ + 0.587 G′ + 0.114 B′ (on gamma-encoded values, hence "luma", not luminance) and scales the colour differences so that they span the same range as Y: 0.713 = 0.5/(1 − 0.299) and 0.564 = 0.5/(1 − 0.114). BT.709 (HD) uses 0.2126, 0.7152, 0.0722 [2], [3].

### Why chroma subsampling works

The human contrast-sensitivity function for colour (red–green, blue–yellow) falls off at much lower spatial frequencies than for luminance: we resolve fine luminance gratings at about 30–60 cycles per degree but colour gratings at only a fraction of that. Storing colour at a quarter of the pixels removes mostly information we could not see anyway [4].

</GoDeeper>

### Exercise 1 (by hand)

Compute Y, Cr, Cb (OpenCV formula) for BGR (0, 100, 200).

<Solution>

Y = 0.299 · 200 + 0.587 · 100 + 0.114 · 0 = 59.8 + 58.7 = **118.5 → 118 or 119**; Cr = 0.713 · (200 − 118.5) + 128 ≈ **186**; Cb = 0.564 · (0 − 118.5) + 128 ≈ **61**.

</Solution>

### Exercise 2 (coding)

Equalise the brightness of `sample-scene.png` converted to colour in two ways: (a) `cv2.equalizeHist` on each of B, G, R; (b) only on Y of YCrCb. Compare the mean HSV saturation (how much of the tint is left) with the original.

<Solution>

```python
import numpy as np
import cv2

img = cv2.cvtColor(cv2.imread("sample-scene.png", cv2.IMREAD_GRAYSCALE), cv2.COLOR_GRAY2BGR)
img[:, :, 2] = cv2.add(img[:, :, 2], 40)                         # give it a reddish tint
a = cv2.merge([cv2.equalizeHist(c) for c in cv2.split(img)])
ycc = cv2.cvtColor(img, cv2.COLOR_BGR2YCrCb)
ycc[:, :, 0] = cv2.equalizeHist(ycc[:, :, 0])
b = cv2.cvtColor(ycc, cv2.COLOR_YCrCb2BGR)
for name, out in [("per-channel", a), ("Y only", b)]:
    s = cv2.cvtColor(out, cv2.COLOR_BGR2HSV)[..., 1].astype(float)
    print(f"{name:11s}: mean saturation {s.mean():.1f} (original {cv2.cvtColor(img, cv2.COLOR_BGR2HSV)[..., 1].mean():.1f})")
```

Output:

```text
per-channel: mean saturation 1.5 (original 79.2)
Y only     : mean saturation 87.1 (original 79.2)
```

Equalising each channel separately destroys the colour balance: the three channels get the same histogram, so the reddish tint disappears (saturation 1.5). Equalising Y keeps the tint (87.1; slightly stronger, because darker pixels with the same Cr, Cb offset have higher HSV saturation) while changing the brightness distribution.

</Solution>
