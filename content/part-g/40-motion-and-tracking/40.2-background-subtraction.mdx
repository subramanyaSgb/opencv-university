# 40.2 Background subtraction

<Definition term="Background subtraction">comparing each new frame to a model of what the scene normally looks like — built from many recent frames, not just the one before it — and marking whatever differs from that model as foreground.</Definition>

40.1 measured a real problem: two-frame differencing on two real moving objects produced four detected blobs, not two. This chapter delivers the fix 14.5 already promised — real `MOG2` and `KNN` background models — and measures, with real numbers, whether it actually works.

## 1. An analogy

Recognising what is new in a room by remembering what it normally looks like, built up over many visits, rather than by comparing only to how it looked a moment ago. A chair that has always been in the corner is never "new", even if you only glance at the room once; something placed there five minutes ago stands out immediately, against that accumulated memory.

## 2. A model, not a snapshot

14.5's "empty reference" and "running average" methods were simple, single-value versions of this idea. `cv2.createBackgroundSubtractorMOG2` keeps a small mixture of Gaussian distributions *per pixel* [1][2], so a pixel that is sometimes one value and sometimes another (a flickering light, a swaying branch) can still be "background" without a single fixed value; `cv2.createBackgroundSubtractorKNN` instead keeps a short history of recent values per pixel and classifies a new value by how many of its nearest neighbours in that history are close to it. Both update continuously, and both compare the *whole* object to a background that never contained it — unlike two-frame differencing, which only ever compares an object to *itself*, one frame later.

## 3. The real fix for 40.1's over-count

Running both real subtractors on exactly the same two-object video 40.1 used:

| Frame | True objects | MOG2 detected blobs | KNN detected blobs |
| --- | --- | --- | --- |
| 0 | 2 | 1 | 1 |
| 3 | 2 | 4 | 1 |
| 5 | 2 | 4 | 2 |
| 6 | 2 | 2 | 2 |
| 20, 30, 40 | 2 | 2 | 2 |

Past frame 6 (MOG2) and frame 4 (KNN), both methods report exactly **2 detected blobs for 2 real objects** — 40.1's 4-blob over-count is genuinely gone. Before that, both are visibly still *learning*: MOG2 briefly reports 4 blobs (behaving almost like two-frame differencing while its per-pixel model is still too thin to be confident), and KNN briefly under-reports at 1. A background model is not instant — it has a real, measurable warm-up cost.

## 4. A worked example: tuning detection vs false positives

MOG2's `varThreshold` controls how far a pixel must be from its modelled distribution to count as foreground. Sweeping it on the same video, at a frame well past the learning period:

| `varThreshold` | Object found | Background false-positive rate |
| --- | --- | --- |
| 4 | 65% | 3.28% |
| 9 | 64% | 0.25% |
| 16 | 64% | 0.00% |
| 36 | 64% | 0.00% |

Raising `varThreshold` from 4 to 16 drives the background false-positive rate from 3.28% to exactly 0%, while the real object-detection rate barely moves (65% → 64%) — a genuine, measured trade-off with a clear, cheap win available: there was no real detection cost to paying for a cleaner background here.

## 5. Industrial context: when a learned background is the right tool

A fixed camera watching a conveyor, a yard, or a doorway — where the background really is mostly stable from frame to frame — is exactly where MOG2/KNN earn their place over plain differencing, delivering Section 3's real one-blob-per-object result instead of 40.1's double-count. The real cost, measured directly in Section 3, is the learning period: a system that must detect correctly from its very first few frames (not after a 4-6 frame warm-up) needs either a pre-built background model (captured before anything is expected to move) or to simply accept a short, bounded inaccurate window at startup.

### 2. OpenCV: real MOG2 and KNN on the same video

```python
# Needs the 60-frame synthetic sequence from 40.1's own setup (see the text)
import cv2

mog2 = cv2.createBackgroundSubtractorMOG2(history=30, varThreshold=16, detectShadows=False)
knn = cv2.createBackgroundSubtractorKNN(history=30, dist2Threshold=400, detectShadows=False)

def blob_count(subtractor, frame):
    mask = subtractor.apply(frame)
    mask = cv2.morphologyEx(mask, cv2.MORPH_CLOSE, np.ones((5, 5), np.uint8))
    n, labels, stats, centroids = cv2.connectedComponentsWithStats(mask)
    return sum(1 for s in stats[1:] if s[4] >= 20)

for t, frame in enumerate(frames):            # frames: the 60-frame synthetic sequence (40.1)
    m, k = blob_count(mog2, frame), blob_count(knn, frame)
    if t in (0, 3, 5, 6, 20):
        print(f"frame {t}: mog2={m} knn={k}")
```

## OpenCV API notes

- **`cv2.createBackgroundSubtractorMOG2(history, varThreshold, detectShadows)`**: `history` sets how many recent frames influence the model; `varThreshold` is the per-pixel Mahalanobis-like distance a sample must exceed to count as foreground (Section 4); `detectShadows=True` (the default) marks detected shadows as 127 instead of 255 — set `False` for a clean binary mask when shadows are not being modelled separately.
- **`cv2.createBackgroundSubtractorKNN(history, dist2Threshold, detectShadows)`**: `dist2Threshold` plays the analogous role to `varThreshold`, on a squared-distance scale against the pixel's recent history rather than a fitted Gaussian mixture.
- **`.apply(frame)`**: both update their internal model *and* return the current foreground mask in the same call — every real frame genuinely changes the model, including frames with no real foreground at all.
- **No separate "reset" needed between videos** — construct a fresh subtractor object per independent video/camera; sharing one across unrelated streams would let one stream's content pollute another's background model.

## Where it fails

- **A moving or panning camera** breaks the whole premise — a pixel's "history" is only meaningful if the same real-world point actually lands there repeatedly; without first stabilising the frames (39.7) or registering them (21.x), every pixel's history is meaningless noise.
- **A long-stationary object gets absorbed into the background** — the same "sleeping object" problem 14.5's running-average method had (Toyama et al. [3], already cited there); a longer `history` delays this, but does not prevent it.
- **Sudden, scene-wide lighting changes** (14.5) can make the whole frame look foreground for a few frames until the model relearns — a real cost this chapter's own measured learning period (Section 3) generalises to any moment the model must re-adapt, not only start-up.

## ⚠️ Common mistakes

<Callout kind="mistake">

- **Expecting a correct mask from the very first frame** — Section 3's own real trace shows both MOG2 and KNN still wrong for several frames before converging; design for a real, bounded startup inaccuracy.
- **Leaving `detectShadows=True`** and thresholding the mask as if it were pure binary — a shadow pixel (value 127) would silently pass a `mask > 0` test while meaning something different from a true foreground pixel (255).
- **Reusing one subtractor object across two unrelated video sources** — its learned model would mix content from both, corrupting the result for either.
- **Tuning only for detection rate and never checking false positives** (or vice versa) — Section 4's real sweep shows both move somewhat independently; check both before picking a setting.

</Callout>

## 🔍 Go deeper

<GoDeeper>

### Why KNN converged faster than MOG2 here

KNN's decision for a new pixel value is a direct comparison against its own stored recent history — as soon as a handful of real samples exist, it already has something concrete to compare against. MOG2 instead fits a *parametric* mixture of Gaussians, which needs a few more real observations before its fitted components are confident enough to classify new samples reliably — a structural, algorithmic reason (not a tuning accident) for the real, measured 2-frame difference in convergence speed this chapter found (KNN by frame 4, MOG2 by frame 6).

### Shadow detection

Both subtractors can model shadows as a distinct class (`detectShadows=True`, the default), based on the insight that a shadowed background pixel keeps roughly the same *hue*, just a lower *value* (brightness) — real shadows and real new objects can usually be told apart on exactly that basis, without needing a separate classifier.

</GoDeeper>

### Exercise 3 (thinking)

A line inspection system needs correct detections starting from the very first frame after a shift-change restart — it cannot tolerate Section 3's real multi-frame learning period. Based on this chapter and 14.5, what real option avoids the wait entirely?

<Solution>

14.5's "empty reference" method, differencing against a single pre-captured image of the truly empty scene, needs **no learning period at all** — it is correct from frame one, provided the empty scene can actually be captured before the line starts (14.5's own stated condition: stable lighting, no scene changes between capture and use). This chapter's MOG2/KNN trade a short, real startup cost for the ability to keep adapting afterward (14.5's running-average idea, done properly); a system that cannot tolerate even a few seconds of reduced accuracy should prefer the empty-reference approach, or seed the background model with a real, pre-captured empty-scene image before the first real frame instead of starting from nothing.
