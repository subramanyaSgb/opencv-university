# 39.2 Codecs and RTSP

<Definition term="RTSP (Real Time Streaming Protocol)">a control protocol a client uses to ask a camera or server to start, pause or stop sending it a *live* video stream — the stream's actual pictures travel separately, over RTP.</Definition>

4.5 already covered what a codec does and how I, P and B frames fit into a GOP. This chapter is about something 4.5 only mentioned in passing: how a live IP camera actually gets its video to you over a network, which is a different problem from reading a file.

## 1. An analogy

RTSP is like phoning a radio station to ask them to start playing a particular channel down a separate line: "please start sending me channel 3." The phone call itself (RTSP) is short — a few polite requests and replies — and then hangs up its *purpose* once the real broadcast (the video, over RTP) is flowing on its own.

## 2. Signalling vs media: two different jobs

RTSP [1] itself carries no video. It is a small text-based request/reply protocol — `OPTIONS` (what can you do?), `DESCRIBE` (what streams do you have, and how are they encoded? — answered with an **SDP**, a Session Description), `SETUP` (let's agree on a transport), `PLAY` (start), `TEARDOWN` (stop). Once `PLAY` succeeds, the actual pictures travel over **RTP** [2], the Real-time Transport Protocol — usually its own UDP packets, sometimes "interleaved" inside the same TCP connection RTSP itself used.

## 3. A real stream, read for real

<RtspLab caption="Illustrative packet loss and damage: UDP can lose a packet and recover by the next I-frame; TCP-interleaved transport never loses a packet but adds latency instead. This is a model, not a live measurement -- Section 3's own numbers below are the real, measured ones."/>

For this chapter, a real `ffmpeg` sent this course's own Module 39.1 clip as RTP over UDP, on this machine, to itself (`127.0.0.1`), and wrote the session description it generated to a `.sdp` file:

```text
v=0
o=- 0 0 IN IP4 127.0.0.1
s=No Name
c=IN IP4 127.0.0.1
t=0 0
m=video 12345 RTP/AVP 96
b=AS:58
a=framerate:25
a=rtpmap:96 H264/90000
a=fmtp:96 packetization-mode=1; sprop-parameter-sets=Z2QAFazZQZCf7wEQAAADABAAAAMDIPFi2WA=,aOvjyyLA; profile-level-id=640015
```

This is a real SDP: `RTP/AVP 96` means payload type 96 carries the media, `rtpmap:96 H264/90000` says that payload is H.264 at a 90 000 Hz **RTP clock rate**, `sprop-parameter-sets` carries the real H.264 SPS/PPS (the decoder configuration, normally sent in-band — here sent once, up front, in the SDP itself), and `b=AS:58` is the real measured bandwidth, 58 kbit/s.

`cv2.VideoCapture` then opened that `.sdp` file and received **108 real decoded frames over 4.03 real seconds** — about 26.8 fps actual, close to the clip's declared 25 fps (Section 4's worked example explains the small difference). This is a genuinely real, local round trip: a real RTP sender, real UDP packets over the loopback interface, and a real H.264 decode on the receiving end.

## 4. A worked example by hand

The SDP's `rtpmap:96 H264/90000` sets the **RTP clock rate** to 90 000 ticks per second — a fixed convention for video RTP, unrelated to the actual frame rate. At 25 fps, each frame is 1/25 s apart, so the RTP timestamp step between frames is:

90 000 ÷ 25 = **3 600 ticks per frame**

This is exactly how a receiver recovers real playback timing from RTP alone: it never needs to know "25 fps" as a separate number — successive packets' timestamps already encode it, 3 600 ticks apart.

The ~26.8 fps actually measured in Section 3, against a declared 25 fps, is not a contradiction: `-re` real-time pacing, Python's own loop overhead, and OS scheduling jitter on a 2-second looping local stream all add a little variance — a live network stream is never as metronomic as reading a file (39.1).

## 5. Industrial context: why cameras use RTSP at all

A machine-vision camera on a line typically hands you **raw, uncompressed frames** through a vendor SDK (GigE Vision, USB3 Vision, 4.5's Section 9) — no RTSP needed, because there is exactly one consumer and no network compression required. An **IP/CCTV camera** watching a yard or a public area is different: it expects *several* possible viewers (an NVR, a live monitoring wall, an occasional engineer's laptop), over a real network, so it speaks the one protocol nearly every NVR and viewer already supports — RTSP for the handshake, H.264/H.265 RTP for the compressed media. A typical camera URL looks like `rtsp://user:pass@192.168.1.64:554/stream1`; `554` is RTSP's default TCP port, and `cv2.VideoCapture` opens it exactly like a file path or index (4.5, Section 9).

```python
import numpy as np

clock_rate_hz = 90_000   # from this chapter's real SDP: rtpmap:96 H264/90000
fps = 25
step = clock_rate_hz // fps
timestamps = np.arange(10) * step
print("ticks per frame:", step)
print("timestamps, frames 0-9:", timestamps)
```

### 3. Reading the real stream with cv2.VideoCapture

```python
# Needs a live RTP sender running concurrently (see Code example 2 and the lesson's Section 3 above)
import os
# This environment variable must be set BEFORE the Python process starts (in the
# launching shell), not with os.environ[...] inside the script -- verified: the
# latter did not take effect in this test, even set before `import cv2`.
print("required beforehand: OPENCV_FFMPEG_CAPTURE_OPTIONS=protocol_whitelist;file,udp,rtp")
import cv2
import time

cap = cv2.VideoCapture("stream.sdp", cv2.CAP_FFMPEG)
print("isOpened:", cap.isOpened(), " fps reported:", cap.get(cv2.CAP_PROP_FPS))
count, t0 = 0, time.time()
while time.time() - t0 < 4.0:
    ok, frame = cap.read()
    if not ok:
        break
    count += 1
elapsed = time.time() - t0
print(f"frames received in {elapsed:.2f}s: {count} ({count / elapsed:.1f} fps actual)")
cap.release()
```

### 4. The real cost of an unreachable camera URL

```python
# Needs a timing run: numbers depend on the machine and the network stack
import cv2
import time

t0 = time.time()
cap = cv2.VideoCapture("rtsp://127.0.0.1:1/missing", cv2.CAP_FFMPEG,
                        (cv2.CAP_PROP_OPEN_TIMEOUT_MSEC, 2000))
print("isOpened:", cap.isOpened(), " elapsed:", round(time.time() - t0, 2), "s")
cap.release()
```

Typical output (one machine):

```text
isOpened: False  elapsed: 2.1 s
```

Without the explicit timeout, the exact same unreachable URL (`cap = cv2.VideoCapture("rtsp://127.0.0.1:1/missing", cv2.CAP_FFMPEG)`) really took about 30 seconds, logging `Stream timeout triggered after 30005.084000 ms` before giving up — confirming `cv2`'s bundled FFmpeg genuinely recognises and attempts `rtsp://` URLs (it does not reject the scheme outright), and that **the default open timeout is real and close to 30 seconds**.

## OpenCV API notes

- **`cv2.VideoCapture(url, apiPreference, params)`**: the three-argument form is the one that reliably applies backend-specific options such as `CAP_PROP_OPEN_TIMEOUT_MSEC` and `CAP_PROP_READ_TIMEOUT_MSEC` — `params` is a flat tuple/list of `(propId, value)` pairs. Calling `.set(CAP_PROP_OPEN_TIMEOUT_MSEC, ...)` on an already-constructed, unopened `cv2.VideoCapture()` **before** `.open(url)` did not shorten the real wait in this test (Code section 4) — always prefer the constructor form for open-time options.
- **`OPENCV_FFMPEG_CAPTURE_OPTIONS`**: an environment variable read by OpenCV's bundled FFmpeg backend, format `key1;value1|key2;value2`. Used here to add `rtp` and `udp` to FFmpeg's default `protocol_whitelist` (`file,crypto,data`), which otherwise refuses to open a raw RTP/UDP stream via an `.sdp` file at all. Must be set in the environment the Python process is launched into — setting it from inside the already-running script did not take effect in this test (Code section 3's comment).
- **`cv2.VideoCapture("stream.sdp", cv2.CAP_FFMPEG)`**: opening a `.sdp` session description file is how OpenCV (via FFmpeg) can receive a raw RTP stream without a full RTSP handshake — exactly the transport layer that a real RTSP `SETUP`/`PLAY` exchange would have negotiated automatically.
- **`CAP_PROP_FOURCC`, `CAP_PROP_FPS`** etc. all work the same on a live stream as on a file (39.1) — this chapter's `fps reported: 25.0` came from the SDP's own `a=framerate:25` line.

## Where it fails

- **This chapter's local system `ffmpeg` binary could not act as an RTSP client or server at all** (`ffmpeg -protocols` lists no `rtsp` entry in this build) — only the lower-level RTP/UDP transport that RTSP negotiates could be tested directly with it; the RTSP handshake itself is described from the protocol standard [1], and confirmed indirectly through `cv2`'s own bundled FFmpeg correctly recognising and attempting `rtsp://` URLs (Code section 4).
- **A camera that is slow to respond, or an address with no camera at all, blocks for a long time by default** (measured here: ~30 seconds) — always set an explicit open/read timeout in production code, never rely on the default.
- **UDP transport can lose packets**; a lost RTP packet damages its frame and, if it carries motion-compensated data, every frame predicted from it until the next I-frame (4.5, RtspLab's model) — TCP-interleaved transport avoids loss but can stall instead, trading one problem for the other.
- **Joining a live stream mid-GOP** (as this chapter's own receiver did, starting a second or so after the sender) can produce real decoder warnings and transient artefacts until the next I-frame arrives — a live stream, unlike a file, has no guaranteed clean starting point.

## ⚠️ Common mistakes

<Callout kind="mistake">

- **Setting `OPENCV_FFMPEG_CAPTURE_OPTIONS` with `os.environ[...]` inside the script**, even before `import cv2` — verified not to take effect in this test; set it in the shell before launching Python instead.
- **Calling `.set(CAP_PROP_OPEN_TIMEOUT_MSEC, ...)` before `.open()`** and assuming it worked — verified to make no difference here; pass the timeout through the constructor's `params` argument instead.
- **Assuming a failed or slow RTSP connection will fail fast** — this chapter measured a real ~30-second default wait; without an explicit timeout, one unreachable camera can stall an entire pipeline.
- **Confusing RTSP (the handshake protocol) with RTP (the media transport)** — a camera "speaking RTSP" is really doing both: a short RTSP conversation, then RTP packets flowing on their own.

</Callout>

## 🔍 Go deeper

<GoDeeper>

### RTCP: RTP's companion

RTP streams are usually paired with **RTCP** (RTP Control Protocol), a low-rate side channel carrying statistics (packets sent, lost, jitter) and synchronisation information between audio and video streams — useful for monitoring stream health, separate from RTSP's one-time setup conversation.

### Multicast

Because RTSP and RTP are separate, a single camera can in principle serve many RTP receivers from one encode — including, where the network supports it, **IP multicast**, so the camera encodes once and the network (not the camera) duplicates packets to every subscribed viewer. Most consumer and small-business IP cameras in practice only support unicast (one encode per viewer), since multicast needs network-wide support that is uncommon outside larger, purpose-built installations. `TODO: verify` exact multicast support varies by camera model and is not something this chapter could test directly.

### ONVIF

Many commercial IP cameras additionally speak **ONVIF**, a higher-level standard built partly on RTSP, that also covers device discovery, PTZ (pan-tilt-zoom) control and event notifications — RTSP handles the video itself, ONVIF wraps it with everything else a camera can do.

</GoDeeper>

<Solution>

Step = 90 000 ÷ 15 = **6 000 ticks per frame**. After 10 frames: 10 × 6 000 = **60 000 ticks**.

### Exercise 3 (thinking)

A colleague wants to switch their 8-camera monitoring wall (4.5's industrial example) from RTSP-over-UDP to RTSP-over-TCP-interleaved transport, reasoning that "TCP never loses packets, so the video will always be perfect." Using RtspLab and this chapter's material, what should they expect instead, and is it strictly an improvement?

<Solution>

They are right that TCP-interleaved transport will not lose packets the way UDP can (RtspLab's "no loss" state) — but TCP achieves that by retransmitting and waiting for lost packets in order, which adds latency and can momentarily stall the whole stream if a packet needs resending, rather than simply dropping one damaged stretch of frames until the next I-frame the way UDP does. For a monitoring wall, which usually prioritises low latency and can tolerate the occasional brief glitch over a GOP, UDP is often still the better practical choice; TCP-interleaved transport trades "occasionally a few damaged frames" for "occasionally the whole stream pauses," which is not strictly better, just a different trade-off (Where it fails).

</Solution>
