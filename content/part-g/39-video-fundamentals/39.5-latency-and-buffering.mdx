# 39.5 Latency and buffering

<Definition term="End-to-end latency">the real time between something happening in front of the camera and your program finding out about it — the sum of every stage's own delay, not just the last one you happen to be looking at.</Definition>

7.4 already covered one important source of latency in depth: a slow processing loop falling behind a camera, and fixing it with a thread that always reads the newest frame. This chapter looks at everything *else* that adds latency along the way — most of it well before your own code ever sees a frame — and measures one of those sources for real.

## 1. An analogy

A letter mailed across the country does not travel at one speed; it waits at a local sorting office, rides a truck, waits at a regional hub, rides a plane, waits at the destination office, then finally reaches you. Total delivery time is the *sum* of every stop's holding time, and the slowest single stop is not necessarily where most of the delay comes from — sometimes it is several merely-moderate stops added together.

Every one of these stages can add delay on its own, and they add up in series. 7.4 covered the last one in detail (a slow processing loop, fixed with a newest-frame reader thread) — this chapter measures one of the earlier, usually-overlooked ones for real: the delay a B-frame-based encoder structure forces onto every single frame, no matter how fast your own code is.

## 3. A real, measured reorder delay

<LatencyBudgetLab caption="This chapter's own real reorder-delay and 39.4's own real decode numbers, stacked with two illustrative sliders into one total latency against a target budget."/>

4.5 already stated that live inspection streams avoid B-frames because they add delay — this chapter measures exactly how much. Encoding this course's own 39.1 clip (25 fps) with `libx264` at three different B-frame settings, then reading the real packet timestamps with `ffprobe`:

| B-frames per GOP (`-bf`) | First packet's PTS | First packet's DTS | Reorder delay |
| --- | --- | --- | --- |
| 0 | 0.000000 s | 0.000000 s | **0 ms** |
| 1 | 0.000000 s | −0.040000 s | **40 ms** |
| 2 | 0.000000 s | −0.080000 s | **80 ms** |

**PTS** (presentation timestamp) says *when* a frame should be shown; **DTS** (decode timestamp) says *when* it must be decoded — which, for a frame sitting behind B-frames, is *earlier* than its own presentation time, because the decoder needs it ready in advance to predict the B-frames that come before it in display order. A negative first DTS is exactly this: the decoder must do real work *before* "time zero" of playback, which means a real receiver must buffer that much data before it can even start displaying frame 0. The pattern is exact: reorder delay = (B-frames per GOP) × (frame period) = `bf` × 40 ms at this clip's 25 fps — 0, 40 and 80 ms, precisely matching the three real measurements.

## 4. A worked example by hand: one real latency budget

Assembling a real budget for one specific, concrete pipeline: `bf=1` encoding (40 ms reorder delay, Section 3), software decode on this course's own test machine (39.4's real 210.7 fps → 1000/210.7 ≈ 4.75 ms per frame), a network/jitter buffer of 60 ms, and 50 ms of application processing:

40 + 4.75 + 60 + 50 = **154.75 ms** total, end to end.

Against a 500 ms alarm-response requirement (a plausible real monitoring target), this leaves 500 − 154.75 = **345.25 ms** of margin — comfortably within budget. Switching to hardware decode (39.4's real 77.3 fps → 1000/77.3 ≈ 12.9 ms) changes the total only to 40 + 12.9 + 60 + 50 = 162.9 ms — on this machine, decode mode barely moves the total, because it was never the dominant term; the encoder's reorder delay and the illustrative network/processing figures matter far more here.

## 5. Industrial context: choosing settings with the real number in hand

4.5's advice ("live inspection streams avoid B-frames") now has a concrete number behind it: every B-frame between anchors on this test clip cost exactly 40 ms, real and measured, not a vague "some delay." A line that must alarm within, say, 200 ms simply cannot afford `bf=2`'s 80 ms before a single other stage is even counted; a recording-only archive stream, where nobody is waiting on the result in real time, can use B-frames freely for the bitrate savings (4.5, Section 7) with no practical cost at all.

**Q1.** A 30 fps encode uses `bf=2`. What is the reorder delay in milliseconds?

<Solution>

## Code

### 1. NumPy: the reorder-delay formula, generalised

```python
import numpy as np

fps = 25
bf_values = np.array([0, 1, 2])
frame_period_ms = 1000 / fps
reorder_delay_ms = bf_values * frame_period_ms
print("reorder delay (ms) for bf = 0, 1, 2:", reorder_delay_ms)
```

Output:

```text
reorder delay (ms) for bf = 0, 1, 2: [ 0. 40. 80.]
```

### 2. The real ffmpeg encode and ffprobe measurement

```bash
ffmpeg -i sample-ball-25fps.mp4 -c:v libx264 -bf 2 -g 50 -pix_fmt yuv420p sample-ball-25fps-bf2.mp4
ffprobe -select_streams v:0 -show_entries packet=pts_time,dts_time,flags -of csv=p=0 sample-ball-25fps-bf2.mp4
```

The real first three lines of output (unedited):

```text
0.000000,-0.080000,K__
0.120000,-0.040000,___
0.040000,0.000000,___
```

`K` marks a keyframe. The first packet's PTS (0.000000) and DTS (−0.080000) differ by exactly 80 ms — Section 3's `bf=2` row, confirmed directly from the real container.

### 3. What cv2.VideoCapture reports instead

```python
import cv2

cap = cv2.VideoCapture("sample-ball-25fps-bf2.mp4")
for i in range(3):
    ok, frame = cap.read()
    print(f"frame {i}: CAP_PROP_POS_MSEC = {cap.get(cv2.CAP_PROP_POS_MSEC):.1f}")
cap.release()
```

Output:

```text
frame 0: CAP_PROP_POS_MSEC = 0.0
frame 1: CAP_PROP_POS_MSEC = 40.0
frame 2: CAP_PROP_POS_MSEC = 80.0
```

These are the real **PTS** times, in presentation order (0, 40, 80 ms — the same values that appear, out of order, scattered through Section 3's own `ffprobe` packet listing: 0.000000, 0.120000, 0.040000, 0.080000, …). `cv2.read()` always hands back frames already sorted into this presentation order — it never exposes the negative decode-order DTS, or the raw decode-order sequence, that revealed the reorder delay in Section 3.

## OpenCV API notes

- **`cv2.VideoCapture` never exposes per-packet DTS** — it only hands you fully decoded frames in presentation order, plus `CAP_PROP_POS_MSEC` (itself derived from PTS, 39.1). Measuring reorder delay (Section 3) genuinely required a packet-level tool (`ffprobe`), not `cv2` itself — a real, confirmed API limitation, not an oversight in this chapter's method.
- **`CAP_PROP_BUFFERSIZE`**: where a backend supports it, requests a shallower internal buffer — fewer frames held means less potential latency from that one stage, at the cost of being less tolerant of brief stalls (7.4).
- **No single property reports "total end-to-end latency"** — Section 4's budget has to be assembled by hand (or measured per-stage) exactly as this chapter did; no API gives you that one number directly.

## Where it fails

- **Network jitter is variable, not fixed** — a real jitter buffer must be sized for the *worst* reasonably-expected delay, not the average, or it will itself drop frames when the network is briefly slower than usual (39.2).
- **A buffer's frame count and its millisecond delay are not the same thing** — a 10-frame buffer is 400 ms of delay at 25 fps but only 167 ms at 60 fps; always convert using the actual frame rate (Mini exercise).
- **Processing-time variance, not just its average, grows latency** — 7.4's buffer-growth problem is driven by the worst sustained stretch of slow frames, not the mean processing time.

## ⚠️ Common mistakes

<Callout kind="mistake">

- **Treating "latency" as one single number to optimise** — Section 2's pipeline has several independent stages; fixing the slowest one (often the application loop, 7.4) may still leave a real, measured cost sitting in the encoder settings (Section 3) that nobody looked at.
- **Choosing encoder settings for bitrate alone** on a stream that will be watched or acted on live — this chapter's own measured 40–80 ms per B-frame is a real, avoidable cost for exactly that use case (Section 5).
- **Confusing a buffer's size in frames with its added delay in milliseconds** — always multiply (or divide) by the frame period to compare the two honestly.
- **Assuming `cv2.VideoCapture` can report encoder-level reorder delay** — it cannot (OpenCV API notes); that measurement needs a different tool.

</Callout>

## 🔍 Go deeper

<GoDeeper>

### Jitter buffers

A real network jitter buffer does not just add a fixed delay — it holds incoming packets briefly so that small, random variations in arrival time (jitter) can be smoothed out before frames are handed to the decoder in a steady stream; sizing it too small lets jitter cause visible stutters or drops, sizing it too large adds latency for no further benefit. Real-world RTP receivers (39.2) typically make this buffer adaptive, growing and shrinking with measured network conditions rather than using one fixed size. `TODO: verify` exact adaptive-sizing algorithms vary by implementation and were not tested directly in this course.

### Low-latency encoder presets

Beyond simply setting `bf=0`, encoders offer dedicated "low-latency" or "zero-latency" presets (for example x264's `-tune zerolatency`) that also disable frame-threading lookahead and other buffering the encoder itself would otherwise use internally, trading some compression efficiency for a more predictable, lower end-to-end delay — relevant for exactly the kind of live-alarm system Section 5 describes.

</GoDeeper>

## Exercises

### Exercise 1 (by hand)

A pipeline has: 60 ms reorder delay, 8 ms decode time, 90 ms network/jitter buffer, and 70 ms processing. Is it within a 200 ms target budget, and by how much?

<Solution>

Total = 60 + 8 + 90 + 70 = **228 ms**. This is **over** the 200 ms budget by 228 − 200 = **28 ms**.

</Solution>

### Exercise 3 (thinking)

A line needs an alarm within 150 ms of a defect appearing. The current pipeline uses `bf=2` at 25 fps (80 ms reorder delay alone, Section 3), plus 50 ms of processing. Using this chapter's real numbers, what is the single cheapest change to make, and why?

<Solution>

The reorder delay alone (80 ms) plus processing (50 ms) is already 130 ms, leaving only 20 ms for everything else (network, decode) — far too tight. The cheapest fix, following Section 5's own argument, is dropping to **`bf=0`**, which this chapter measured as exactly **0 ms** reorder delay (Section 3's own table) — a pure latency win with no code changes needed, only an encoder setting, unlike reducing processing time which would require actual algorithmic work.

</Solution>
