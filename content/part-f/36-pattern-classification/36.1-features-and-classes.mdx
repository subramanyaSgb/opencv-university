# 36.1 Features and classes

<Definition term="Classification">deciding which one of several predefined categories (classes) an object belongs to, based on a set of measurements (a feature vector) taken from it, not on the raw image itself.</Definition>

Modules 33–35 spent a great deal of effort turning pixels into numbers: a corner's location, a descriptor, a texture histogram, a HOG vector. This module asks the next question: given those numbers, which **category** does this thing belong to? That is classification, and it turns out to need surprisingly little new machinery once the features are good — which is exactly why so much of this course, so far, has been about building good features.

## 1. An analogy

A fruit seller sorting produce by weight and colour into three bins: apples, lemons, grapes. Nobody needs to see a photograph of the fruit — two numbers (weight, colour) are usually enough, *if* those two numbers happen to separate the three kinds of fruit well. Classification is choosing a bin from measurements; the whole art is in choosing measurements that actually separate the bins.

## 2. Feature vectors, feature space, classes

- A **feature vector** is just a list of numbers measured from one object: `(mean grey level, standard deviation)` is a 2-D feature vector; a 1764-number HOG descriptor (35.3) is a 1764-D one.
- **Feature space** is the space those vectors live in — for 2 features, a plane you can plot and look at directly; for more features, the same idea in more dimensions, impossible to draw but not conceptually different.
- A **class** is one of the predefined categories the classifier must choose between (e.g. "woven," "smooth," "blotchy"; or "defect," "no defect"). Classes are defined by the task, not discovered by the algorithm — compare with **clustering** (36.8), which groups data *without* predefined classes.
- A **classifier** is a rule that, given a new feature vector, outputs a class. The simplest possible rule — and the one used below — is: compute the **centroid** (mean feature vector) of each class from known examples, and assign a new point to whichever centroid it is nearest. This is the starting idea behind k-nearest-neighbours (36.3), formalised properly there.

## 3. A worked example by hand

Three classes, one example feature vector (mean grey level, standard deviation) each:

| Class | Mean | Std. dev. |
| --- | --- | --- |
| Woven | 145.5 | 33.9 |
| Smooth | 139.9 | 13.3 |
| Blotchy | 136.6 | 49.6 |

A new point: (142.6, 5.1). Distance to each centroid (Euclidean, √(Δmean² + Δstd²)):

- To Woven: √((142.6−145.5)² + (5.1−33.9)²) = √(8.4 + 829.4) = **28.9**
- To Smooth: √((142.6−139.9)² + (5.1−13.3)²) = √(7.3 + 67.2) = **8.6**
- To Blotchy: √((142.6−136.6)² + (5.1−49.6)²) = √(36.0 + 1980.3) = **44.9**

Nearest is **Smooth** (8.6), by a wide margin. This new point was, in fact, measured from the "missing weave" defect patch of 35.1 — a patch *of the woven fabric* with its texture erased. In (mean, std) feature space, it looks nothing like "Woven": it looks like "Smooth," because that is what a low-standard-deviation patch looks like to these two features, regardless of what produced it.

## 4. A real feature space, tile by tile

<FeatureSpaceLab caption="Each dot is one 8x8 tile's (mean, std) from the woven/smooth/blotchy textures (35.1); black circles are the class centroids. Click anywhere to drop a test point and see which centroid is nearest."/>

Splitting each 72×72 texture image into 81 non-overlapping 8×8 tiles and computing (mean, std) per tile gives a real 2-D feature space, 81 points per class:

| Class | Centroid mean | Centroid std |
| --- | --- | --- |
| Woven | 145.49 | 33.54 |
| Smooth | 139.93 | 4.50 |
| Blotchy | 136.56 | 27.56 |

One specific tile, cut from inside the "missing weave" defect patch (tile column 3, row 3 of `sample-texture-defect.png`): mean 142.77, std 4.93. Distances to the three centroids above: Woven 28.74, **Smooth 2.87**, Blotchy 23.46 — nearest to Smooth, again by a wide margin, for the same reason as Section 3: locally, a patch with no weave pattern simply *is* smooth, by these two features. (Note the Smooth centroid's std here, 4.50, is much lower than the whole-image std reported in 35.1, 13.3 — a single 8×8 tile of a slowly-varying image has far less internal variation than the whole image does across all its slow variation; always know exactly what region a feature is being measured over.)

## 5. Industrial use

- **Sorting and grading**: any task where a part must be assigned to one of a known, fixed set of categories (grade A/B/C; pass/fail; part type 1/2/3) from measured features.
- **Defect classification** (not just detection): once something is flagged as unusual (as Section 3's example might be), a classifier can further say *which kind* of defect it resembles, if trained on examples of each kind.
- **Every subsequent chapter in this module** builds a more capable classifier than "nearest centroid" — but every one of them still starts from a feature vector and predefined classes, exactly as described here.

## Mini exercise

**Q1.** Two classes, 1-D feature (just a single number): class A's examples average to 10, class B's average to 50. Where would a new point at 25 be classified, by nearest centroid?

<Solution>

Distance to A = |25−10| = 15. Distance to B = |25−50| = 25. Nearer to **A**.

</Solution>

**Q2.** Why couldn't (mean, std) distinguish the defect patch from "Smooth," in Sections 3–4, even though a person can immediately tell a photo of plain smooth shading from a photo of fabric with a flaw?

<Solution>

Because a person is using far more information than just two numbers — overall layout, context, the surrounding weave pattern, edges at the defect's border. (Mean, std) only describes the *statistics of grey values inside one small patch*, which genuinely is similar between the two cases. The fix is not a smarter classifier but **better features** — e.g. the LBP or GLCM descriptors of 35.1–35.2, which do capture local pattern structure that (mean, std) throws away.

</Solution>

## Code

### 1. The worked example, and the tile feature space, with NumPy

```python
import numpy as np
import cv2

centroids = {"woven": (145.5, 33.9), "smooth": (139.9, 13.3), "blotchy": (136.6, 49.6)}
point = (142.6, 5.1)
for name, c in centroids.items():
    d = np.hypot(point[0] - c[0], point[1] - c[1])
    print(f"distance to {name}: {d:.1f}")

TILE = 8
def tile_features(img, label):
    h, w = img.shape
    feats = []
    for ty in range(h // TILE):
        for tx in range(w // TILE):
            patch = img[ty * TILE:(ty + 1) * TILE, tx * TILE:(tx + 1) * TILE].astype(np.float64)
            feats.append((patch.mean(), patch.std(), label))
    return feats

classes = {}
for name in ["woven", "smooth", "blotchy"]:
    img = cv2.imread(f"sample-texture-{name}.png", cv2.IMREAD_GRAYSCALE)
    classes[name] = tile_features(img, name)

centroids_real = {name: (np.mean([f[0] for f in feats]), np.mean([f[1] for f in feats])) for name, feats in classes.items()}
for name, c in centroids_real.items():
    print(f"{name}: {len(classes[name])} tiles, centroid ({c[0]:.2f}, {c[1]:.2f})")
```

Output:

```text
distance to woven: 28.9
distance to smooth: 8.6
distance to blotchy: 44.9
woven: 81 tiles, centroid (145.49, 33.54)
smooth: 81 tiles, centroid (139.93, 4.50)
blotchy: 81 tiles, centroid (136.56, 27.56)
```

### 2. Classifying one tile of the defect image by nearest centroid

defect = cv2.imread("sample-texture-defect.png", cv2.IMREAD_GRAYSCALE)

## OpenCV API notes

- **No dedicated OpenCV function for "nearest-centroid classification"** — it is three lines of NumPy (as above). OpenCV's `ml` module provides full classifiers (`cv2.ml.KNearest`, `cv2.ml.SVM`, `cv2.ml.NormalBayesClassifier`, `cv2.ml.RTrees`, `cv2.ml.Boost`, among others), introduced properly as this module goes on (36.2–36.6).
- **`cv2.ml` classifiers share a common interface**: `.train(samples, layout, responses)` where `layout` is `cv2.ml.ROW_SAMPLE` (each row is one feature vector) or `cv2.ml.COL_SAMPLE`, and `.predict(samples)` returns predicted labels — the same pattern every chapter from 36.2 on will use.
- **Feature scaling matters for distance-based methods**: here, "std" (roughly 0–50) and "mean" (roughly 80–200) are on different scales; a feature with naturally larger numbers can dominate a Euclidean distance even if it's not more informative. (Both features above happen to work reasonably at their natural scales, but normalising features to comparable ranges — e.g. subtracting the mean and dividing by the standard deviation of each feature across the training set — is standard practice before any distance-based classifier.)

## Where it fails

- **A classifier cannot separate classes its features don't separate** — Section 3's whole point. No algorithm fixes bad or insufficient features; better features (more of them, or more discriminative ones) are usually the real fix.
- **Nearest-centroid assumes each class forms one compact, roughly round cluster** around its mean — classes shaped like crescents, rings, or with several separate sub-groups are not well described by a single centroid (36.3's k-nearest-neighbours and 36.4's SVM handle more complex shapes).
- **Centroids computed from very few examples are unreliable** — one or two examples per class (as in Section 3) is a teaching simplification; real classifiers need enough labelled examples to estimate class statistics reliably (Module 58 covers datasets and splits in depth).
- **Outliers skew a centroid**: a single mislabelled or unusual training example shifts the mean of its whole class.

## ⚠️ Common mistakes

<Callout kind="mistake">

- **Confusing classification with clustering**: classification assigns to *predefined* classes; clustering (36.8) discovers groups with no predefined labels. If you don't already know the categories, you want clustering, not classification.
- **Expecting more features to always help**: an uninformative or noisy feature can *hurt* a distance-based classifier by adding irrelevant variation to the distance calculation — feature selection matters as much as feature creation.
- **Not normalising features of very different scales** before computing distances (OpenCV API notes above).
- **Judging a feature space by eye in 2-D and assuming the same intuition holds in high dimensions** — 2-D plots (as in Section 4) are great for building intuition, but real feature vectors are often tens, hundreds or thousands of dimensions, where "nearest" and "compact cluster" behave somewhat differently (the so-called curse of dimensionality, touched on again in 36.3).

</Callout>

## 🔍 Go deeper

<GoDeeper>

### Supervised vs unsupervised learning

Classification (this module, mostly) is **supervised learning**: training examples come with known class labels. Clustering (36.8) is **unsupervised**: no labels, only the data's own structure. Many real systems combine both — cluster first to discover structure, then hand-label the clusters and classify new data against them.

### The curse of dimensionality

As the number of features grows, the volume of feature space grows exponentially, and a fixed number of training examples covers it ever more sparsely; "nearest neighbour" distances between points also tend to become less discriminative (everything ends up roughly equally far from everything else) unless the data has real low-dimensional structure. This motivates both careful feature selection and dimensionality reduction (PCA, 36.7) before classification.

### Generative vs discriminative classifiers

Nearest-centroid implicitly assumes classes are shaped like simple blobs around their means. Bayes classifiers (36.2) make this assumption explicit and probabilistic (a **generative** model: how likely is this feature vector, given each class?). SVMs (36.4) instead focus directly on the boundary between classes (a **discriminative** model), without necessarily modelling each class's full distribution.

</GoDeeper>

## Exercises

### Exercise 1 (by hand)

Two classes in 2-D: class A centroid (0, 0), class B centroid (8, 0). Classify the points (3, 0) and (5, 0) by nearest centroid.

<Solution>

(3, 0): distance to A = 3, to B = 5 → **A**.
(5, 0): distance to A = 5, to B = 3 → **B**.
The midpoint, (4, 0), would be exactly tied — the decision boundary for nearest-centroid between two classes is always the perpendicular bisector of the line joining their centroids.

</Solution>

### Exercise 3 (thinking)

A colleague proposes classifying industrial parts as "defective" or "good" using a single feature: the part's average brightness. Before building anything, what question should you ask them?

<Solution>

Essentially Section 3's question: **does average brightness actually differ between defective and good parts, for the defects you care about?** If defects are things like cracks, scratches, or missing features that don't change the overall average brightness (as this chapter's defect patch did not), a brightness-only classifier will fail regardless of how it's implemented — not because the method is wrong, but because the one feature chosen doesn't carry the information needed. The right next step is to look at real examples of both classes and find a feature (texture, edges, shape, a learned feature) that actually separates them, before investing in a classifier.

</Solution>
