# 38.3 OCR engines

<Definition term="OCR engine">the component that takes a segmented character (38.2) and decides which letter or digit it actually is — by comparing it against known examples, classically, or (in a modern engine like Tesseract) by running it through a trained model.</Definition>

38.2 cut a line of text into individual character boxes. This chapter builds the piece that actually reads one: starting from the simplest possible version — compare each character against a set of reference templates, pick the closest — built entirely from tools this course already has (32.1–32.2's `cv2.matchTemplate`), then looking at what a real, industrial-strength OCR engine does differently.

## 1. An analogy

Matching a found puzzle piece against a set of reference shapes by holding it over each one and seeing which it fits best. For a small, fixed set of possible shapes (ten digits, a handful of letters), this works — exactly the problem 38.3's first half solves. A real OCR engine instead has learned, from an enormous number of real examples, what *every* letter tends to look like across countless fonts, sizes and amounts of damage — closer to a human reader's experience than to literally holding up a stencil.

## 2. Template matching as the simplest OCR

<Flow
  steps={[
    { label: "Reference templates, one per character", tone: "data" },
    { label: "Segmented character (38.2)", tone: "process" },
    { label: "Compare to every template (32.1-32.2's NCC)", tone: "process" },

/>

- **Templates**: one reference image per possible character, rendered (or captured) the same way the text to be read will appear.
- **Comparison**: 32.2's normalised cross-correlation (NCC) between the segmented character and each template — the same metric, used for a new purpose.
- **Decision**: the template with the highest NCC score wins; its label is the recognised character.
- **The catch**: this only works well when the character being read looks *close enough* to its template — same rough size, same font, same orientation. Real print rarely cooperates perfectly, which is exactly where this simple approach starts to struggle (Section 4).

## 3. A worked example by hand

Two tiny 2×2 templates: A = `[[1,0],[0,1]]`, B = `[[0,1],[1,0]]`. A segmented glyph reads `[[1,0],[0,1]]`.

SSD (32.1) to A: compare cell by cell — (1−1)² + (0−0)² + (0−0)² + (1−1)² = 0. SSD to B: (1−0)² + (0−1)² + (0−1)² + (1−0)² = 1+1+1+1 = **4**. A's SSD (0) is far lower than B's (4) — the glyph is recognised as **A**, a perfect match.

Beyond that, the glyph is literally too big for the fixed-size comparison used here, and the method breaks completely rather than degrading gracefully.

## 5. What a real OCR engine does instead

Tesseract — the most widely used open-source OCR engine, and the one `pytesseract` wraps — does not compare against a handful of fixed templates. ## Mini exercise

**Q1.** Templates C = `[[1,1],[0,0]]`, D = `[[0,0],[1,1]]`. A glyph reads `[[1,1],[0,1]]`. Which template has the lower SSD?

<Solution>

SSD to C: (1−1)²+(1−1)²+(0−0)²+(1−0)² = 0+0+0+1 = 1. SSD to D: (1−0)²+(1−0)²+(0−1)²+(1−1)² = 1+1+1+0 = 3. **C** has the lower SSD (1 vs 3) and is the better match.

</Solution>

**Q2.** Why did the scale-mismatch test's score drop from 1.000 to about 0.76 even though the character was still correctly recognised?

<Solution>

Normalised cross-correlation measures how well-aligned the glyph and template are, pixel for pixel; a slightly larger glyph no longer lines up exactly with the template's stroke positions, even though the overall shape is still closer to the correct template than to any other — "still the best match" and "still a strong, confident match" are different things, and the dropping score is an early warning sign of exactly the brittleness Section 4 goes on to show breaking outright at a bigger size difference.

</Solution>

## Code

### 1. The worked example, and a real template recognizer with NumPy

```python
import numpy as np
import cv2

A = np.array([[1, 0], [0, 1]])
B = np.array([[0, 1], [1, 0]])
glyph = np.array([[1, 0], [0, 1]])
print("SSD to A:", int(((glyph - A) ** 2).sum()))
print("SSD to B:", int(((glyph - B) ** 2).sum()))

CANVAS = 34
def pad_center(g):
    h, w = g.shape
    if h > CANVAS or w > CANVAS:
        return None
    out = np.zeros((CANVAS, CANVAS), np.uint8)
    y0, x0 = (CANVAS - h) // 2, (CANVAS - w) // 2
    out[y0:y0 + h, x0:x0 + w] = g
    return out

def render_char(ch, scale=1.2):
    img = np.full((70, 70), 255, np.uint8)
    cv2.putText(img, ch, (10, 52), cv2.FONT_HERSHEY_SIMPLEX, scale, 0, 2, cv2.LINE_AA)
    _, bw = cv2.threshold(img, 128, 255, cv2.THRESH_BINARY_INV)
    ys, xs = np.where(bw > 0)
    return bw[ys.min():ys.max() + 1, xs.min():xs.max() + 1]

templates = {ch: pad_center(render_char(ch)) for ch in "LOT0123456789"}

def classify(glyph_img, templates):
    g = pad_center(glyph_img)
    if g is None:
        return None, None
    best_ch, best_score = None, -1.0
    for ch, t in templates.items():
        score = float(cv2.matchTemplate(g.astype(np.float32), t.astype(np.float32), cv2.TM_CCOEFF_NORMED)[0, 0])
        if score > best_score:
            best_score, best_ch = score, ch
    return best_ch, best_score

img = cv2.imread("sample-charseg-text.png", cv2.IMREAD_GRAYSCALE)
_, bw = cv2.threshold(img, 128, 255, cv2.THRESH_BINARY_INV)
n, labels, stats, _ = cv2.connectedComponentsWithStats(bw)
boxes = sorted([tuple(stats[i][:4]) for i in range(1, n)], key=lambda b: b[0])

result = ""
for (x, y, w, h) in boxes:
    ch, score = classify(bw[y:y + h, x:x + w], templates)
    result += ch
    print(f"glyph at x={x}: predicted '{ch}', score {score:.3f}")
print("recognised string:", result)
```

Output:

```text
SSD to A: 0
SSD to B: 4
glyph at x=13: predicted 'L', score 1.000
glyph at x=33: predicted 'O', score 0.855
glyph at x=57: predicted 'T', score 0.993
glyph at x=78: predicted '4', score 1.000
glyph at x=102: predicted '2', score 1.000
recognised string: LOT42
```

## OpenCV API notes

- **No built-in OCR in OpenCV core**: `cv2.matchTemplate` (Section 4) is a general tool, not an OCR-specific one; OpenCV's `cv2.dnn` module can run a separately-downloaded text-recognition neural network, but ships no model and no text-reading function out of the box.
- **`pytesseract`** (a thin Python wrapper around the separately-installed Tesseract engine, not part of `cv2` at all): `.image_to_string(image)` for plain text, `.image_to_data(image, output_type=Output.DICT)` for per-word boxes and a confidence score (`data["conf"]`) — genuinely useful output this chapter's template matcher does not provide (it only returns a label and a score per *given* box, having relied on 38.2 to find the boxes in the first place).
- **Page segmentation mode (`--psm`, a pytesseract/Tesseract config option)**: tells Tesseract how to expect the text to be laid out (a single line, a single word, sparse text, etc.) — worth setting explicitly for short, structured industrial text rather than leaving Tesseract to guess a full page's layout.

## Where it fails

- **Template matching needs the glyph's size, font and orientation to closely match the templates** — Section 4 demonstrated this breaking down directly, first gracefully (lower scores) and then completely (glyph too large for the comparison canvas).
- **A fixed template set cannot recognise anything it wasn't given a template for**: an unexpected character, font variant, or symbol has no chance of being matched correctly.
- **No language model or context**: a template matcher (or Tesseract run on isolated characters) has no way to use "this is probably a word in a known vocabulary" to fix an ambiguous character the way word-level or line-level recognition can.
- **This course cannot verify Tesseract's actual output directly**, since it isn't installed in the pinned verification environment — Section 5's Tesseract-related code is accordingly illustrative, not a checked result, consistently marked as such.

## ⚠️ Common mistakes

<Callout kind="mistake">

- **Assuming a template-matching recognizer will generalise to new fonts or sizes** without testing — Section 4's own numbers show measurable degradation well before outright failure.
- **Treating a high match score as proof of correctness** without also checking it's meaningfully higher than the next-best template's score — a narrow win is less trustworthy than a landslide one.
- **Confusing `cv2.matchTemplate`-based character recognition (this chapter) with full OCR**: real OCR also needs line/word segmentation, layout analysis and often a language model — this chapter deliberately isolated just the "which character is this" step, already solved by 38.2's boxes.
- **Running Tesseract-dependent code without checking it is actually installed** — a `pytesseract` call fails outright if the underlying Tesseract binary isn't present on the system, independent of whether the Python package itself is installed.

</Callout>

## 🔍 Go deeper

<GoDeeper>

### Why Tesseract moved to LSTMs

Earlier Tesseract versions (pre-4.0) used a more classical feature-and-classifier pipeline, broadly similar in spirit to this chapter's approach but considerably more sophisticated (adaptive templates, multiple feature types). Version 4 introduced an LSTM-based line-recognition engine [1], reading a whole text line at once rather than character by character, letting the model use the context of neighbouring characters the way word-level recognition benefits from — directly addressing the "no context" limitation this chapter's isolated-character approach has.

### Confidence scores and downstream filtering

Tesseract's `image_to_data` confidence per word (0–100, not used by this chapter's own NCC score) lets a pipeline automatically flag low-confidence reads for human review, rather than accepting every result uncritically — a standard, important part of deploying any OCR system in a setting where errors have a real cost (lot numbers feeding an inventory system, say).

### Beyond Tesseract: learned, end-to-end text recognition

Modern deep-learning text recognisers (CRNNs and transformer-based models, Part J) often skip explicit character segmentation entirely, reading a whole cropped word image directly into a string — the same "whole line, not character by character" idea Tesseract's LSTM engine already uses, taken further.

</GoDeeper>

## Exercises

### Exercise 1 (by hand)

Templates E = `[[1,1],[1,0]]`, F = `[[0,1],[1,1]]`. A glyph reads `[[1,1],[1,1]]`. Compute SSD to both and decide the match.

<Solution>

SSD to E: (1−1)²+(1−1)²+(1−1)²+(1−0)² = 0+0+0+1 = 1. SSD to F: (1−0)²+(1−1)²+(1−1)²+(1−1)² = 1+0+0+0 = 1. **Tied** — both templates are equally close (SSD 1 each); a real system would need a tie-breaking rule, or more discriminative templates, since this glyph genuinely sits exactly between the two.

</Solution>

### Exercise 2 (coding)

Using the Code section's `classify` and `templates`, test a "4" rendered with `cv2.FONT_HERSHEY_DUPLEX` instead of `FONT_HERSHEY_SIMPLEX` (a different font, same size) and report the predicted character and score.

<Solution>

```python
def render_char_font(ch, font):
    img = np.full((70, 70), 255, np.uint8)
    cv2.putText(img, ch, (10, 52), font, 1.2, 0, 2, cv2.LINE_AA)
    _, bw = cv2.threshold(img, 128, 255, cv2.THRESH_BINARY_INV)
    ys, xs = np.where(bw > 0)
    return bw[ys.min():ys.max() + 1, xs.min():xs.max() + 1]

g = render_char_font("4", cv2.FONT_HERSHEY_DUPLEX)
ch, score = classify(g, templates)
print(f"different font: predicted {ch}, score {score:.3f}")
```

Output:

```text
different font: predicted 4, score 0.687
```

Still correct, but with a markedly lower score (0.687) than the same-font case (1.000) — even lower than the scale-mismatch degradation in Section 4 (0.76). A different font changes the glyph's exact stroke shapes even at the same nominal size, degrading the match for the same underlying reason as the scale mismatch: template matching compares pixels directly, with no tolerance for shape variation beyond what the comparison canvas and NCC happen to forgive.

</Solution>

### Exercise 3 (thinking)

A factory wants to read a fixed 6-digit lot code, always printed in the same font and size by the same label printer. Is Section 4's template-matching approach, or a full engine like Tesseract, the better fit here?

<Solution>

Given the font, size and character set are all fixed and known in advance — exactly the conditions under which Section 4's template matcher worked perfectly (and the conditions under which it fails, font/size variation, 38.3's whole lesson, simply don't apply here) — the simple template-matching approach is a entirely reasonable, fast, fully explainable choice, with no external dependency on an engine like Tesseract that this course cannot even verify in its own environment. A full OCR engine would be the better choice if the label printer, font, or text format ever varied, or if free-form text needed reading — neither of which this fixed, controlled lot-code scenario requires.

</Solution>
