# 42.3 Disparity

<Definition term="Disparity map">a real, per-pixel measurement of how far each point shifted between a rectified stereo pair's two images (42.2) — the actual quantity 42.1's `Z = f.B/d` formula needs, computed from real image content instead of assumed known.</Definition>

42.1 assumed disparity was already known; 42.2 explained why, after rectification, it only needs a 1D search. This chapter actually runs that search, with `cv2.StereoBM` and `cv2.StereoSGBM`, and measures a real, sometimes surprising trade-off in doing so.

## 1. An analogy

Finding the same word on two otherwise-identical pages, one slightly shifted print run of the other: for most words, sliding a small window along the line until the letters match tells you exactly how far it shifted. For a blank, featureless stretch of page, there is nothing to slide-and-match against — any shift looks equally "correct," which is exactly why disparity matching fails on featureless regions.

## 2. Block matching, and a real quality-control knob

<Flow
  steps={[
    { label: "Two rectified images, epipolar lines horizontal (42.2)", tone: "data" },
    { label: "For each pixel, slide a small block along its row in the other image", tone: "process" },
    { label: "Find the best match (lowest difference); check it is clearly the best, not a tie", tone: "process" },
    { label: "A real disparity value, or 'no confident match' if the check fails", tone: "result" },
  ]}
/>

`cv2.StereoBM` slides a small block along each row, scoring how well it matches at every candidate shift, and keeps the best-scoring shift as that pixel's disparity — but only if `uniquenessRatio` (how much better the best match must be than the next-best) and `textureThreshold` (how much real local contrast a block must have) are both satisfied. Fail either check, and that pixel gets no disparity value at all, rather than a guessed one.

## 3. A real, measured coverage-vs-accuracy trade-off

<DisparityLab caption="Real cv2.StereoBM/StereoSGBM results on a synthetic, known-disparity (16 px) textured plane. Compare the real coverage and accuracy of each configuration."/>

A synthetic textured plane with a real, known 16 px disparity, matched with `cv2.StereoBM`:

| Configuration | Coverage | Mean disparity |
| --- | --- | --- |
| Default (`uniquenessRatio=15`) | 2.8% | 16.79 px |
| Relaxed (`uniquenessRatio=0`) | 77.9% | 16.19 px |

A real, isolated test confirmed `textureThreshold` had **zero** effect on this result — this particular synthetic texture always has plenty of local contrast. `uniquenessRatio` alone caused the entire coverage change: the strict default rejected 97.2% of pixels as "not a unique enough match," even though the few it kept, and nearly all of the ones it rejected, were in fact close to the true 16 px value. Relaxing it to 0 gave both far more coverage **and** a slightly better mean accuracy on this real test.

## 4. A real comparison: BM vs SGBM

`cv2.StereoSGBM` (Semi-Global Block Matching) adds a real smoothness constraint across neighbouring pixels, intended to give denser, more consistent results than plain block matching. On the identical synthetic data, its default settings gave **65.4%** coverage, mean disparity **14.73 px** (farther from the true 16 than BM-relaxed's 16.19), with a real measured standard deviation of **8.73 px** — noisier per-pixel than BM-relaxed, despite a reasonable-looking mean. Neither algorithm is simply "better" in every real sense; each has its own real trade-offs, confirmed here rather than assumed from either method's reputation.

## 5. Industrial context: from disparity to a usable depth map

Once a real disparity map exists, 42.1's own formula, `Z = f.B/d`, applied pixel by pixel, gives a full depth map directly — exactly how a real stereo camera product turns two 2D images into a 3D point cloud. Section 3's own coverage numbers matter here directly: a sparse 2.8%-coverage disparity map gives a sparse, hole-filled depth map, while this chapter's own relaxed settings (or a better-textured real scene) fill in far more of it — the real, practical reason stereo depth cameras are often marketed with notes about needing "sufficient texture" in the scene.

## Code

### 1. NumPy: a known-disparity synthetic test pair

```python
import numpy as np

rng = np.random.default_rng(9)
H, W, NUM_DISP, TRUE_DISPARITY = 240, 320, 32, 16
texture = rng.integers(0, 255, (H, W + NUM_DISP + 20), dtype=np.uint8)
left = texture[:, NUM_DISP + 10:NUM_DISP + 10 + W]
right = texture[:, NUM_DISP + 10 - TRUE_DISPARITY:NUM_DISP + 10 - TRUE_DISPARITY + W]
print("left/right shapes:", left.shape, right.shape)
```

Output:

```text
left/right shapes: (240, 320) (240, 320)
```

### 2. OpenCV: real BM, the real parameter effect, and real SGBM

```python
import cv2

stereo = cv2.StereoBM_create(numDisparities=32, blockSize=15)
disp_default = stereo.compute(left, right).astype(np.float32) / 16.0
valid_default = disp_default > 0
print(f"BM default: coverage {valid_default.mean()*100:.1f}%, mean {disp_default[valid_default].mean():.2f}")

stereo.setUniquenessRatio(0)
stereo.setTextureThreshold(0)
disp_relaxed = stereo.compute(left, right).astype(np.float32) / 16.0
valid_relaxed = disp_relaxed > 0
print(f"BM relaxed: coverage {valid_relaxed.mean()*100:.1f}%, mean {disp_relaxed[valid_relaxed].mean():.2f}")

sgbm = cv2.StereoSGBM_create(minDisparity=0, numDisparities=32, blockSize=15)
disp_sgbm = sgbm.compute(left, right).astype(np.float32) / 16.0
valid_sgbm = disp_sgbm > 0
print(f"SGBM default: coverage {valid_sgbm.mean()*100:.1f}%, mean {disp_sgbm[valid_sgbm].mean():.2f}")
```

Output:

```text
BM default: coverage 2.8%, mean 16.79
BM relaxed: coverage 77.9%, mean 16.19
SGBM default: coverage 65.4%, mean 14.73
```

## OpenCV API notes

- **`cv2.StereoBM_create(numDisparities, blockSize)`**: `.compute(left, right)` returns a fixed-point `int16` disparity map scaled by 16 (Code section 2 divides by `16.0` to get real pixel units); invalid pixels are marked `-16` (i.e., `-1` after scaling).
- **`setUniquenessRatio`, `setTextureThreshold`**: real, tunable quality-control parameters — this chapter's own test shows `uniquenessRatio` can dominate coverage entirely, with `textureThreshold` doing nothing on a texture-rich scene.
- **`cv2.StereoSGBM_create(minDisparity, numDisparities, blockSize[, ...])`**: has its own, different set of real tuning parameters (`P1`, `P2` smoothness penalties, `mode`) not explored in this chapter's basic default-settings comparison.
- **Both algorithms need already-rectified input** (42.2) — running either on unrectified images searches the wrong direction entirely, since the real epipolar lines are not horizontal.

## Where it fails

- **A genuinely flat, featureless real scene** (not this chapter's noise-rich synthetic texture) fails `textureThreshold` directly — no amount of relaxing `uniquenessRatio` recovers real information that was never there (Mini exercise).
- **Repetitive real texture** (a regular grid, a striped pattern) can genuinely confuse block matching with multiple, equally-plausible wrong disparities — exactly the kind of real ambiguity `uniquenessRatio` is meant to catch, at the real cost Section 3 measured.
- **This chapter's own relaxed-threshold result being more accurate is not a general rule** — it reflects this specific synthetic texture's own properties; a real scene with genuine repetitive ambiguity could see relaxed thresholds let through real, confidently-wrong matches instead.

## ⚠️ Common mistakes

<Callout kind="mistake">

- **Assuming BM's default settings are always well-tuned** — Section 3's own real result (2.8% coverage from the identical data) shows the default can be far too conservative for some real scenes.
- **Treating low disparity-map coverage as broken code** rather than checking real scene texture and the real `uniquenessRatio`/`textureThreshold` settings first.
- **Assuming SGBM is strictly better than BM** because of its added smoothness constraint — Section 4's own real comparison found SGBM noisier (higher std) than relaxed BM on this specific test.
- **Running stereo matching on unrectified images** (42.2) — the whole real block-matching search direction assumes horizontal epipolar lines.

</Callout>

## 🔍 Go deeper

<GoDeeper>

### Why uniqueness checking exists at all

A block match that scores nearly identically well at two different disparities is genuinely ambiguous — picking either one with full confidence would be a real mistake. `uniquenessRatio` exists to catch exactly this case and withhold a value rather than guess; this chapter's own synthetic pure-noise test happened to trigger that caution far more often than it needed to, a real, instructive edge case rather than a general flaw in the idea.

### Beyond classical block matching

Modern dense stereo methods increasingly use learned (deep-network) cost functions and regularisation instead of SGBM's hand-designed smoothness penalty, often achieving denser, more accurate results on genuinely difficult real scenes (repetitive texture, thin structures, reflective surfaces) than either classical method this chapter tested — a real, active area the classical `cv2.StereoBM`/`StereoSGBM` methods predate.

</GoDeeper>

### Exercise 3 (thinking)

A colleague's stereo depth camera gives very sparse depth on a shiny metal part but dense depth on its matte-painted edges. Based on this chapter, what is the most likely real explanation?

<Solution>

A shiny metal surface often shows specular highlights and reflections that genuinely differ between the two cameras' slightly different viewpoints — the same real patch of metal can look different enough in each image that block matching finds no confident, unique match (Section 2's uniqueness check, Where it fails' repetitive/ambiguous-texture case), while the matte-painted edges keep a real, consistent appearance from both viewpoints and match normally. This is a real, physical limitation of passive stereo on reflective surfaces, not a software bug to tune away with `uniquenessRatio` alone.

</Solution>
