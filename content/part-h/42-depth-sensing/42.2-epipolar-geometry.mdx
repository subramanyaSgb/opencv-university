# 42.2 Epipolar geometry

<Definition term="Epipolar constraint">the real geometric fact that a point's match in a second camera's image cannot be anywhere in 2D — it must lie on one specific line, determined entirely by the two cameras' known relative pose (41.8), regardless of the point's actual, unknown depth.</Definition>

42.1 assumed disparity was already known. This chapter explains *why* stereo matching only ever needs to search along one line, not the whole second image — a real, exact geometric constraint, not an approximation or a convenient simplification.

## 1. An analogy

Looking through a narrow slot in a fence at a point, then walking sideways to a second known position: whatever you see through the fence from the new spot, the original point (wherever its real, unknown distance actually is) must appear somewhere along one particular direction from the new spot — never off to some other, unrelated direction. That one direction is the epipolar line.

## 2. The real constraint, in one equation

For a real stereo pair (42.1's own setup: `R = I`, baseline 120 mm), the essential matrix `E = [t]_x R` and fundamental matrix `F = K⁻ᵗ E K⁻¹` (converting between real-world and pixel units) work out to:

```text
E = [[0, 0, 0], [0, 0, 120], [0, -120, 0]]
F = [[0, 0, 0], [0, 0, 0.15], [0, -0.15, 0]]
```

For real corresponding points `x1`, `x2` (homogeneous pixel coordinates), the epipolar constraint `x2ᵗ F x1 = 0` held **exactly**, to displayed precision, for every true correspondence tested.

## 3. Recovering F from points alone, and a real test

<EpipolarLab caption="A real fundamental matrix F for a real, slightly misaligned stereo pair. Click a point in the left image; its match in the right image lies exactly on the computed line, at any depth."/>

`cv2.findFundamentalMat` recovers `F` from point correspondences alone — no known camera pose required. On 20 real correspondences (the same stereo setup), it recovered an `F` matching the analytical structure exactly; checking a held-out point's real match against its computed epipolar line gave a distance of **5.6 × 10⁻¹⁴ px** — exact, not approximate.

For a real, slightly *misaligned* pair (a small rotation plus a non-purely-horizontal translation — a realistic imperfectly-mounted stereo rig), the same point, placed at two different real depths (`Z = 800` mm and `Z = 1500` mm), projects to two genuinely different pixel positions in the second image — but **both land exactly on the same computed epipolar line**. The line tells you *where* the match must be; it never tells you *how far along it* without more information (42.1's disparity, or 42.3's actual matching).

## 4. Making the lines horizontal: a real, practical payoff

`cv2.stereoRectify` re-projects both cameras' images so their epipolar lines become perfectly horizontal — turning the general, possibly-tilted line of Section 3 into the simple, row-only search 42.1's `Z = f.B/d` formula assumed all along. On the same real, misaligned pair, a test point's row coordinate before rectification differed between the two cameras; after rectification, it became `253.96005730249837` in camera 1 and `253.96005730249843` in camera 2 — identical to 12 significant figures. This is exactly what 42.3's dense disparity matching needs to search efficiently.

## 5. Industrial context: why this underlies every real stereo system

Every real stereo product — from a depth camera to a two-camera inspection rig — rectifies its images first, using exactly this chapter's method, before running any dense matching at all. Skipping rectification does not make stereo matching impossible, just far more expensive: a 2D search over the whole second image, instead of Section 4's real, much cheaper 1D search along one row.

## Code

### 1. NumPy: the essential and fundamental matrices, from scratch

```python
import numpy as np

K = np.array([[800.0, 0, 320], [0, 800.0, 240], [0, 0, 1]])
t = np.array([-120.0, 0, 0])
R = np.eye(3)

tx = np.array([[0, -t[2], t[1]], [t[2], 0, -t[0]], [-t[1], t[0], 0]])
E = tx @ R
F = np.linalg.inv(K).T @ E @ np.linalg.inv(K)
print("E =\n", E)
print("F =\n", F)
```

Output:

```text
E =
 [[   0.    0.    0.]
 [   0.    0.  120.]
 [   0. -120.    0.]]
F =
 [[ 0.    0.    0.  ]
 [ 0.    0.    0.15]
 [ 0.   -0.15  0.  ]]
```

### 2. OpenCV: real fundamental matrix recovery, and the epipolar-line check

```python
import cv2

rng = np.random.default_rng(5)
pts3d = rng.uniform([-100, -100, 800], [100, 100, 1500], (20, 3))
img1, _ = cv2.projectPoints(pts3d, np.zeros(3), np.zeros(3), K, None)
img2, _ = cv2.projectPoints(pts3d, np.zeros(3), t, K, None)
img1 = img1.reshape(-1, 2).astype(np.float32)
img2 = img2.reshape(-1, 2).astype(np.float32)

F_est, mask = cv2.findFundamentalMat(img1, img2, cv2.FM_8POINT)
x1 = np.array([img1[0, 0], img1[0, 1], 1])
l2 = F_est @ x1
a, b, c = l2
x2 = img2[0]
dist = abs(a * x2[0] + b * x2[1] + c) / np.sqrt(a**2 + b**2)
print("point distance from its real epipolar line (px):", dist)
```

Output:

```text
point distance from its real epipolar line (px): 5.584474978516136e-14
```

## OpenCV API notes

- **`cv2.findFundamentalMat(points1, points2, method)`**: `cv2.FM_8POINT` uses the classic linear 8-point algorithm [1]; `cv2.FM_RANSAC` is the real, robust choice when some correspondences might be wrong matches (34.x's own RANSAC pattern, applied here).
- **`cv2.computeCorrespondEpilines(points, whichImage, F)`**: returns the actual epipolar line (as `[a, b, c]` for `au + bv + c = 0`) for a set of points — the same computation Code section 2 did by hand.
- **`cv2.stereoRectify(K1, d1, K2, d2, imageSize, R, t)`**: returns rectification rotations `R1, R2` and new projection matrices `P1, P2`; applying `R1`/`R2` to each camera's own view and reprojecting with the new `P1`/`P2` is exactly what makes Section 4's real row-matching result possible.
- **`E` vs `F`**: `E` relates normalised (unit-focal-length) camera coordinates; `F` relates real pixel coordinates — `F = K2⁻ᵗ E K1⁻¹`, exactly Code section 1's own conversion.

## Where it fails

- **The 8-point algorithm needs real, well-spread correspondences** — points clustered in one small image region, or too close to a degenerate configuration (all on one 3D plane, for some methods), give a poorly-conditioned or wrong `F`.
- **Real correspondences always carry some matching error** — this chapter's own exact result used perfectly accurate synthetic correspondences; 42.3's real block-matching introduces real pixel-level noise into exactly this constraint.
- **A genuinely wrong assumed camera pose** (41.8) propagates directly into a wrong `F`/epipolar geometry — this chapter's exactness depended on 41.8's own already-verified, accurate baseline.

## ⚠️ Common mistakes

<Callout kind="mistake">

- **Expecting the epipolar line to pin down a point's exact match** — Section 3's own real test shows the identical line holding at two very different real depths; the line narrows the search, it does not finish it.
- **Running dense stereo matching (42.3) on raw, unrectified images** — Section 4's real, measured row-matching result is only available after `cv2.stereoRectify`; skipping it forces a far more expensive 2D search.
- **Confusing E and F**, or using one where the other is needed — `E` works in normalised coordinates, `F` in real pixels; Code section 1's explicit conversion exists precisely because mixing them up gives numerically wrong results.
- **Assuming `cv2.FM_8POINT` is robust to mismatched correspondences** — it assumes every input pair is a genuinely correct match; `cv2.FM_RANSAC` (OpenCV API notes) is the real, robust alternative when that is not guaranteed.

</Callout>

## 🔍 Go deeper

<GoDeeper>

### Why exactly 8 points

The fundamental matrix has 9 real entries but is only defined up to an overall scale (a homogeneous quantity) and satisfies one further real constraint (`det(F) = 0`), leaving 7 genuinely free real parameters — the 8-point algorithm [1] uses one extra point beyond the theoretical minimum (7) specifically for a simpler, purely linear solution, at a small real cost in noise sensitivity compared to more elaborate 7-point methods.

### Epipoles

Every epipolar line in one image passes through a single common point — the **epipole**, the projection of the *other* camera's own position into this image. For the simple horizontal-baseline case in Section 2, the epipole sits at infinity (every epipolar line is a horizontal line, none of which ever meet at a finite point) — exactly why a clean, rectified horizontal-baseline stereo pair's epipolar geometry looks so simple compared to the general, tilted-line case Section 3 demonstrated.

</GoDeeper>

## Exercises

### Exercise 1 (by hand)

A stereo pair has E = [[0,0,0],[0,0,80],[0,-80,0]] and K = diag(1000,1000,1) with principal point (0,0) for simplicity. What is F?

<Solution>

Since K is diagonal with equal fx=fy=1000 and zero principal point, K⁻¹ = diag(0.001, 0.001, 1). F = K⁻ᵗ E K⁻¹ scales the relevant E entries by (0.001)² = 1e-6: **F = [[0,0,0],[0,0,0.00008],[0,-0.00008,0]]**.

</Solution>

### Exercise 3 (thinking)

A colleague wants to skip `cv2.stereoRectify` entirely, reasoning "we can just use the general, tilted epipolar lines directly for matching." Based on Section 4-5, what real cost would this have?

<Solution>

It is mathematically possible — the epipolar constraint (Section 2-3) holds regardless of whether the pair is rectified — but Section 4's real measurement shows rectification turns the search into a simple row-only (1D, horizontal) comparison; without it, matching along a general, tilted line for every pixel is real, additional computational and implementation complexity for no real geometric benefit, since the constraint itself does not require horizontal lines, only rectification's own convenience does. Section 5's point stands: every real stereo system rectifies first specifically to avoid this unnecessary extra cost.

</Solution>
