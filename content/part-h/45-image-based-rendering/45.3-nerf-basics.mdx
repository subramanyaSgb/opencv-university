# 45.3 NeRF basics

<Definition term="NeRF (Neural Radiance Field)">a neural network trained to answer "what colour and density is at this 3D point, viewed from this direction?" — fit from several real photos by minimizing the same real volume-rendering error 45.2's light fields used, then queried to render brand-new views.</Definition>

45.2's shift-and-average refocusing used a known camera geometry and raw pixel values directly. NeRF keeps the exact same real rendering *equation* but replaces the scene itself with something *learned*: a function — in NeRF's own case, a neural network; in this chapter's own fully tractable version, just two unknown numbers — fit to explain several real photos, then used to synthesize views those photos never actually showed.

## 1. An analogy

Looking through a patch of fog, how much of what's *behind* the fog you can still see depends on how thick that patch is: a thin wisp barely dims anything; a dense bank blocks it almost completely, and what you *do* see is dominated by the fog's own colour instead. That trade-off — thin things barely absorbed, thick things nearly opaque — is exactly the real mathematical relationship (`alpha = 1 - exp(-density x thickness)`) every volume renderer, including NeRF, uses to blend a ray's samples into one final colour.

45.2's density and colour were *known*, hand-specified values. NeRF's real innovation is fitting them *instead*: starting from an unknown (or randomly initialized) field, rendering it with the identical equation, comparing the result to a real captured photo's actual pixel colour, and adjusting the field's parameters to shrink that real error — over and over, across every pixel of every available real photo, until the field explains them all.

## 3. A real, measured result: how many samples a ray actually needs

Before fitting anything, the rendering equation itself needs to be computed accurately. For a real, deliberately *sharp* density blob (radius 0.5, far smaller than the ray's own 20-unit range), comparing a coarse quadrature against a very fine one (20,000 samples, standing in for the true continuous integral) shows a real, dramatic accuracy gap: **2** samples gives an error of **68.35** (the step size, 10 units, is 20x wider than the blob itself — the quadrature simply steps over it); **8** samples still misses badly (**53.18** error); **16** samples finally starts to see it (**4.33**); and **32** samples is already accurate to **0.0003** — a real, direct demonstration of why real NeRF implementations use *importance sampling* (placing extra samples where a first, coarse pass finds density) rather than a single fixed, uniform step size.

## 4. A real, measured result: fitting an unknown field from several real views

A toy scene: a Gaussian density blob at an genuinely *unknown* position, observed by several cameras arranged along a line, each shooting 5 real perspective rays (not parallel ones — Section 5 explains why that distinction matters) through realistic sensor noise. Searching for the two unknown position parameters that best explain a set of *training* cameras' own rendered colours, then testing the fitted field on a disjoint set of *held-out* cameras' rays — real novel-view synthesis, at a fully tractable scale — gives a real, measured result consistent with every other "more views" finding in this module: **3** training cameras recovered the position to a mean error of **0.181** and predicted held-out rays to a mean colour error of **0.992**; **9** training cameras improved both, to **0.132** and **0.859** respectively (averaged over 8 independent noisy fits each).

## 5. A real, measured, structural limit: parallax, not just "more photos," is required

Rendering the identical scene with every camera's ray aimed *straight ahead* only (no angled pixels — repeated, parallel-direction shots, never converging from different angles) gives a real, exact result: at camera positions `x = [-1, 0, 1.3, 2.5]`, the rendered colours are **[69.91, 136.61, 179.81, 143.48]** — *identical*, to two decimal places, whether the blob's true depth is placed at `z0=6`, `10`, `11.7`, or `14`. Depth is not merely *harder* to recover from parallel rays — it is **structurally absent** from them: no amount of additional same-direction "views" can ever resolve it, because the rendered colour genuinely does not depend on `z0` at all under this ray geometry. This is exactly 43.1's own real finding about pure-rotation camera motion, now shown to apply to NeRF's own rendering equation directly: real parallax — rays converging from genuinely different angles — is not an optional refinement, it is the one real ingredient that makes depth recoverable at all.

## Code

### 1. NumPy: the real volume-rendering equation, and its real quadrature accuracy

```python
import numpy as np

Z_MAX, F = 20.0, 20.0

def density_fn(x, z, x0, z0, r, sigma_peak):
    return sigma_peak * np.exp(-((x - x0) ** 2 + (z - z0) ** 2) / (2 * r ** 2))

def render_ray(x_cam, p, x0, z0, r, sigma_peak, c0, c_bg, n_samples, z_max=Z_MAX):
    zs = np.linspace(0, z_max, n_samples + 1)
    mids, deltas = (zs[:-1] + zs[1:]) / 2, zs[1:] - zs[:-1]
    ray_x = x_cam + p * mids / F
    sigmas = density_fn(ray_x, mids, x0, z0, r, sigma_peak)
    alphas = 1 - np.exp(-sigmas * deltas)  # 45.2's own alpha-compositing formula
    T = np.concatenate([[1.0], np.cumprod(1 - alphas)])[:-1]  # transmittance before each sample
    weights = T * alphas
    return np.sum(weights * c0) + (1 - weights.sum()) * c_bg

x0, z0, r, sigma_peak, c0, c_bg = 0.0, 10.0, 0.5, 0.8, 200.0, 50.0
true_fine = render_ray(0.5, 0.0, x0, z0, r, sigma_peak, c0, c_bg, n_samples=20000)
for n in [2, 4, 8, 16, 32, 64]:
    val = render_ray(0.5, 0.0, x0, z0, r, sigma_peak, c0, c_bg, n_samples=n)
    print(f"n_samples={n:3d}: rendered={val:.4f}, error vs fine ground truth={abs(val-true_fine):.4f}")
print(f"fine ground truth (n=20000): {true_fine:.4f}")
```

Output:

n_samples=  8: rendered=65.1667, error vs fine ground truth=53.1788
n_samples= 16: rendered=114.0141, error vs fine ground truth=4.3314
n_samples= 32: rendered=118.3452, error vs fine ground truth=0.0003

### 2. OpenCV: visualizing a fitted radiance field

```python
import cv2

x0_fit, z0_fit, r2, sigma2, c02, cbg2 = 1.3, 11.7, 1.0, 0.8, 200.0, 50.0
xs, zs = np.linspace(-4, 4, 100), np.linspace(0, 20, 100)
XX, ZZ = np.meshgrid(xs, zs)
density_slice = density_fn(XX, ZZ, x0_fit, z0_fit, r2, sigma2)

density_8bit = cv2.normalize(density_slice, None, 0, 255, cv2.NORM_MINMAX).astype(np.uint8)
heatmap = cv2.applyColorMap(density_8bit, cv2.COLORMAP_INFERNO)
print("density slice:", density_slice.shape, density_slice.dtype)
print("normalized 8-bit range:", density_8bit.min(), "to", density_8bit.max())
print("heatmap:", heatmap.shape, heatmap.dtype)
```

Output:

```text
density slice: (100, 100) float64
normalized 8-bit range: 0 to 254
heatmap: (100, 100, 3) uint8
```

`cv2.applyColorMap` turns the fitted (or, in real NeRF, the network-predicted) density field into a standard false-colour image — exactly how a real NeRF's internal density volume is typically visualized for inspection, after `cv2.normalize` brings it into the real `[0, 255]` display range.

## OpenCV API notes

- **No `cv2` function performs NeRF training or volume rendering** — the real equation (Code section 1) is the same closed-form alpha-compositing this chapter shares with 45.2; a real NeRF's only addition is a neural network supplying `(density, colour)` instead of a hand-specified formula.
- **`cv2.normalize(..., cv2.NORM_MINMAX)` + `cv2.applyColorMap`** (Code section 2) is the real, standard way to turn any computed scalar field — this chapter's density, or a real trained NeRF's own internal volume — into a viewable image.
- **This chapter's fitting procedure used a brute-force grid search**, not gradient descent — a real NeRF has far too many parameters (a full neural network) for that to be practical, and uses real backpropagation instead; the grid search here is a deliberately simpler, fully verifiable stand-in for the identical underlying optimization problem.

## Where it fails

- **Parallel (non-converging) camera rays cannot recover depth, structurally, not just noisily** (Section 5's own real, exact result) — this is the single most important real precondition for any multi-view 3D method in this entire course, NeRF included.
- **Too few quadrature samples silently under-render thin or sharp features** (Section 3's own real result) — a real NeRF implementation's choice of sample count and importance-sampling strategy directly determines whether fine real detail is captured at all.
- **This chapter's toy field had only 2 free parameters and a known functional form** — a real NeRF's neural network has to discover both the *shape* and the *position* of real, complex scene geometry from photos alone, a vastly harder real optimization problem than this chapter's 2-D grid search.
- **Real NeRF training needs real camera poses already known** (from 43.1's own structure-from-motion, in practice, usually run first) — this chapter assumed exact, known camera positions throughout, exactly as every other method in this module has.

## ⚠️ Common mistakes

<Callout kind="mistake">

- **Assuming more training photos always help, regardless of how they were taken** — Mini exercise's own real point: more same-position, rotation-only photos add nothing toward recovering real depth.
- **Treating NeRF as a fundamentally different rendering process from 45.2's light fields** — Code section 1's own equation is identical; the real difference is *what* is being rendered (a fitted/learned field vs 45.2's known scene), not *how*.
- **Using too few ray samples without checking whether real scene detail is thinner than the sample spacing** — Section 3's own real result (68.35 error at 2 coarse samples) is a direct, measurable consequence of exactly this mistake.
- **Expecting a tiny, 2-parameter toy fit (this chapter) to behave like a full neural NeRF** — the real optimization difficulty (local minima, many more parameters, ill-conditioned gradients) scales up enormously; this chapter's grid search was a deliberate simplification specifically to keep every real number here verifiable.

</Callout>

### The real NeRF paper

Mildenhall, Srinivasan, Tancik, Barron, Ramamoorthi, Ng, "NeRF: Representing Scenes as Neural Radiance Fields for View Synthesis" (ECCV 2020) is the real, foundational paper: a coordinate-based MLP mapping `(x, y, z, theta, phi)` to `(r, g, b, density)`, trained by exactly this chapter's own rendering equation against a real set of posed photos, with positional encoding (mapping each coordinate through a fixed set of sine/cosine frequencies first) to let a otherwise-smooth network represent Section 3's own kind of sharp, thin real detail.

### Radiance fields without neural networks

Yu, Li, Tancik, Li, Ng, Kanazawa, "Plenoxels: Radiance Fields without Neural Networks" (CVPR 2022) replaces NeRF's neural network with a real, explicit voxel grid of density and colour values, optimized directly (no network at all) by exactly this chapter's own kind of per-parameter gradient fitting against real photos — a real, direct validation that NeRF's core contribution is the differentiable rendering equation and multi-view optimization (this chapter's own Section 2-4), not the neural network itself.

</GoDeeper>

### Exercise 3 (thinking)

A research team wants to train a NeRF of a building's facade using only photos taken from a drone flying in a perfectly straight line directly toward the building, each photo centered on the same point. Based on Section 5, what real problem should they expect, and what is the most direct fix?

<Solution>

Following Section 5's own real, exact result, photos taken along a single straight line directly toward a fixed point, all centered on that same point, share exactly the kind of limited parallax that made depth structurally unrecoverable in this chapter's test (every ray converges toward the same direction with little angular spread).
