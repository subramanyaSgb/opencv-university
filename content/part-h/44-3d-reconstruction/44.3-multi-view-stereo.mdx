# 44.3 Multi-view stereo

<Definition term="Multi-view stereo (MVS)">recovering dense depth by combining MANY calibrated views of a scene, not just the two 42.1/42.3 used — each extra view adds another real, independent check against the same candidate depth.</Definition>

42.3's dense disparity search matched exactly two images. A real multi-camera rig, or 43.1's own chained structure-from-motion poses, usually provides far more than two calibrated views of the same scene — and using all of them, not just a pair, is multi-view stereo's whole real point.

## 1. An analogy

Looking at a picket fence from directly in line with it, every picket lines up with every other one — it is genuinely impossible to tell, from that single vantage point, how far away the fence actually is. Stepping even slightly to one side breaks that illusion instantly; stepping to several different new positions breaks it even more thoroughly, because it becomes vanishingly unlikely that *every* new vantage point would happen to show the same false alignment. Multi-view stereo is exactly this: checking a candidate depth from several real, different positions at once, rather than trusting a single potentially-misleading pair.

## 2. The pipeline: plane-sweep stereo

**Plane-sweep stereo** tests a whole range of candidate depths directly, one at a time: for a given candidate depth, every other view is warped (42.1/34.6's own homography machinery, specialized to a simple shift for a flat, fronto-parallel surface) onto the reference view's pixel grid, exactly as if that candidate depth were correct. If the candidate is right, every warped view should show the *same* real intensity at that pixel — low variance across all of them. If it's wrong, the views drift apart — high variance. Sweeping every candidate depth and keeping the one with the lowest variance, independently at every pixel, is the whole real method; this chapter's own test data shows exactly how much better that gets with more views.

## 3. A real, measured result: more views average out real noise

With ordinary (non-repetitive) texture and realistic sensor noise added to every view, two views alone recovered the true 1000mm depth to a mean error of **129.70mm** — only **17.5%** of pixels landed within 10mm of the truth. Adding more views (same noise level, same texture) genuinely helps, because the variance-based consistency check at each candidate depth now averages over more independent noisy measurements: **5** views cut the mean error to **25.90mm** (**84.5%** within 10mm), and **9** views reached **2.88mm** (**99.0%** within 10mm) — a real, roughly 45x improvement in mean error from four extra views beyond the original pair.

## 4. A real, measured result: more views resolve a real ambiguity, not just noise

A *repetitive* texture — the real hazard this chapter's analogy named directly — adds a second, genuinely different source of error on top of the same sensor noise: two views alone gave a mean error of **57.65mm** here (worse than the ordinary-texture case's 129.70mm might suggest it should be, in the opposite direction — a repetitive pattern can look *falsely* consistent at a wrong depth, not just noisily uncertain at the right one). Extra, differently-spaced views fix this the same real way they fixed Section 3's noise: **5** views brought the mean error to **8.85mm**, and **9** views reached **6.22mm** — because a false match that happens to align two closely-spaced views rarely also aligns a view spaced much farther away, exactly 42.5's baseline-sensitivity principle working in this method's favour instead of against it.

## 5. The one real failure more views cannot fix

Running the identical experiment on a genuinely **textureless** region (the same sensor noise, but with essentially no real texture signal at all) gives a real, different, and important result: mean error stays at **136.47mm** with 2 views, **137.53mm** with 5, and **148.55mm** with 9 — not better, and if anything very slightly *worse*. More views cannot manufacture information that was never there to begin with; with no real signal to match, the variance-minimization search is just as likely to settle on an accidentally-low-variance wrong depth as a right one, and more candidate views only add more chances for an accidental false minimum to appear.

## 6. Industrial context: from many photos to one dense reconstruction

A real photogrammetry pipeline — reconstructing a building facade, a manufactured part for reverse engineering, or a VFX film set — routinely captures dozens to hundreds of overlapping photos, recovers their relative poses with 43.1's structure from motion, and then runs exactly this chapter's plane-sweep (or a closely related patch-based variant) across every usable group of views to get one real, dense depth map per reference image — which 44.1's point-cloud cleanup then merges into a single combined model. Multi-view stereo is the real bridge between 43.1's sparse set of feature points and a genuinely dense reconstruction.

## Code

### 1. NumPy: plane-sweep stereo, and its real noise-averaging benefit

```python
import numpy as np

F, Z_TRUE, W = 800.0, 1000.0, 3000
rng = np.random.default_rng(42)
texture = 128 + rng.normal(0, 40, W)  # ordinary, non-repetitive texture

PMIN, PMAX = -600, 900
PIX_RANGE = np.arange(PMIN, PMAX)
REF_PIXELS = np.arange(50, 250)
DEPTH_CANDIDATES = np.arange(700, 1301, 5)

def lookup(arr, p):
    idx = np.clip(p - PMIN, 0, len(arr) - 2)
    i0 = np.floor(idx).astype(int)
    return arr[i0] * (1 - (idx - i0)) + arr[i0 + 1] * (idx - i0)

def sample_texture(pos):
    pos_c = np.clip(pos, 0, W - 2)
    i0 = np.floor(pos_c).astype(int)
    return texture[i0] * (1 - (pos_c - i0)) + texture[i0 + 1] * (pos_c - i0)

def render_camera(cam_x, noise_std, seed):
    wx = cam_x + PIX_RANGE * Z_TRUE / F
    return sample_texture(wx) + np.random.default_rng(seed).normal(0, noise_std, len(PIX_RANGE))

def plane_sweep(n_cams, spacing, noise_std, seed_base):
    cam_positions = np.arange(n_cams) * spacing
    observed = [render_camera(cx, noise_std, seed_base + i) for i, cx in enumerate(cam_positions)]
    variances = np.zeros((len(DEPTH_CANDIDATES), len(REF_PIXELS)))
    for di, d in enumerate(DEPTH_CANDIDATES):
        wx_ref = cam_positions[0] + REF_PIXELS * d / F
        vals = [lookup(observed[ci], (wx_ref - cx) * F / d) for ci, cx in enumerate(cam_positions)]
        variances[di] = np.array(vals).var(axis=0)
    best = DEPTH_CANDIDATES[np.argmin(variances, axis=0)]
    return np.abs(best - Z_TRUE)

for n_cams in [2, 5, 9]:
    err = plane_sweep(n_cams, spacing=50.0, noise_std=5.0, seed_base=100)
    print(f"{n_cams} views: mean error={err.mean():.2f}mm, within 10mm={np.mean(err<=10)*100:.1f}%")
```

Output:

```text
2 views: mean error=129.70mm, within 10mm=17.5%
5 views: mean error=25.90mm, within 10mm=84.5%
9 views: mean error=2.88mm, within 10mm=99.0%
```

### 2. OpenCV: the real warp step

```python
import cv2

baseline, Z = 50.0, 1000.0
disparity_px = F * baseline / Z  # the pure horizontal shift a fronto-parallel plane produces
H = np.array([[1, 0, disparity_px], [0, 1, 0], [0, 0, 1]], dtype=np.float64)

img1 = np.random.default_rng(1).integers(0, 255, (50, 300), dtype=np.uint8)
warped = cv2.warpPerspective(img1, H, (300, 50))
manual_shift = np.allclose(warped[:, int(disparity_px):250].astype(float), img1[:, :250 - int(disparity_px)].astype(float), atol=1)
print(f"disparity at true depth: {disparity_px:.1f}px")
print("cv2.warpPerspective matches a manual pixel shift:", manual_shift)
```

Output:

```text
disparity at true depth: 40.0px
cv2.warpPerspective matches a manual pixel shift: True
```

This is the real, standard way a 2-D plane-sweep implementation performs its "warp every view onto the reference at this candidate depth" step — `cv2.warpPerspective` with a homography built from the candidate plane, run once per view per candidate depth, exactly generalizing this chapter's 1-D pixel-shift model.

## OpenCV API notes

- **No single `cv2` function performs plane-sweep multi-view stereo** — it is a real, standard *algorithm* built from ordinary pieces: `cv2.warpPerspective` (or `cv2.remap`) for the warp step, plain NumPy for the per-pixel variance search across candidate depths.
- **`cv2.warpPerspective(src, H, dsize)`** (Code section 2) takes a `3x3` homography `H`; for this chapter's fronto-parallel-plane case, `H` reduces to a pure horizontal translation by the real disparity (`f x baseline / Z`) that candidate depth implies — exactly 42.1/42.3's own disparity formula, reused here per candidate rather than solved for directly.
- **A general (non-fronto-parallel) scene needs a different homography per candidate plane orientation**, not just per depth — this chapter simplified to a flat, camera-facing surface; a real implementation sweeps both depth and, where needed, surface orientation.

## Where it fails

- **A genuinely textureless region is not helped by more views** (Section 5's own real result) — the real fix there is adding texture (a projected pattern, 42.4), not more cameras.
- **Occlusion**: a point visible in only some of the N views contributes no useful information from the views that cannot see it at all, and a naive variance computed across *all* N views (as this chapter's own simple implementation does) is biased by whichever views are occluded; a real system must detect and exclude occluded views per candidate, similar in spirit to 44.2's own shadow-aware fix.
- **Cost grows with both view count and the number of candidate depths** — this chapter's 121-candidate, 9-view sweep is already real, measurable work; a real dense 2-D image at many more candidate depths and views is substantially more expensive than 42.3's simple two-view disparity search.
- **This chapter's fronto-parallel-plane simplification does not generalize to curved or sharply-angled real surfaces** without sweeping surface orientation as well as depth (OpenCV API notes).

## ⚠️ Common mistakes

<Callout kind="mistake">

- **Assuming more views always help** — Section 5's own real, measured counterexample (a textureless region getting *slightly worse*, not better, from 2 to 9 views) is the direct, honest exception.
- **Treating noise-driven and ambiguity-driven errors as the same problem** — Section 3 and Section 4's own real, different starting errors (129.70mm vs 57.65mm at 2 views) show these are genuinely different failure modes, both real, both fixed by more views, but for different underlying reasons.
- **Forgetting that occlusion needs explicit handling** (Where it fails) — a naive all-views-equal variance, as used throughout this chapter for clarity, silently degrades wherever some views cannot actually see a given point.
- **Searching too coarse a depth range** — this chapter's 5mm candidate step is itself a real source of residual error (Section 3's 9-view "99.0% within 10mm," not 100%); a finer step trades real accuracy for real extra cost.

</Callout>

## 🔍 Go deeper

<GoDeeper>

### Multi-baseline stereo

M. Okutomi, T. Kanade, "A Multiple-Baseline Stereo" (*IEEE Transactions on Pattern Analysis and Machine Intelligence*, 1993) is the real, foundational paper behind Section 4's own result: combining several *different* baselines (not just more of the same one) specifically defeats the kind of repetitive-texture false match that any single baseline alone is vulnerable to, because a false match's apparent depth genuinely depends on which baseline produced it, while the true match's depth does not.

### Patch-based multi-view stereo (PMVS)

Real, modern multi-view stereo (Furukawa, Ponce, "Accurate, Dense, and Robust Multiview Stereopatch, " IEEE TPAMI, 2010) grows a 3D reconstruction from sparse, reliable seed points (43.1's own structure-from-motion output) outward across small oriented patches, checking photo-consistency much like this chapter's variance test but adaptively, rather than sweeping every candidate depth everywhere uniformly — a real, more efficient version of this chapter's own brute-force sweep.

</GoDeeper>
